# TameTravel specification

## Behavior and native feasibility

TameTravel accompanies a player's validated traversal between linked outdoor vanilla portals with that player's explicitly following or portal-waiting tames. It never teleports the player, changes native player portal restrictions, performs general distance catch-up or transports into dungeons. Enabled defaults true; each module remains independent.

The installed client and dedicated-server portal methods execute normal travel on the owning client. TeleportWorldTrigger requires Player.m_localPlayer; TeleportWorld.Teleport checks restrictions and calls Player.TeleportTo without a portal-use RPC. Player.UpdateTeleport publishes its changed transform through ordinary replication. The approved contract is therefore observed traversal: fresh authenticated following, source-trigger crossing, an unchanged reciprocal portal pair, corresponding arrival and readiness constraints. It does not establish the client's internal call site. Shared observation qualifications belong in [limitations](../limitations.md#tametravel).

The public-map marker is another position consumer: Player.LateUpdate sets ZNet's reference position; ServerSyncedPlayerData sends it every two seconds; PlayerList distributes public positions. Minimap.UpdatePlayerPins animates the marker toward updates at 200 metres per second. That animation does not describe a physical path through the world. TameTravel samples actual character ZDO positions and does not require public map visibility. RequestZDO, private teleport flags and local PortalsUsed statistics supply no additional causal portal event. Taking player ownership or replacing player travel would interfere with native controls/inventory restrictions and is excluded.

## Supported objects and following

Normal chat commands are `!follow`, `!stay` and `!wait`; `!tame` requests concise command help. Follow grants fresh consent and starts native following. Stay stops following and cancels consent. Wait requires this player's existing confirmed association or a fresh authenticated request addressing an animal currently following that uniquely named player, stops native following and retains fresh single-trip consent while the animal stays within FollowerRangeMeters of its waiting position. Waiting animals must also be within FollowerRangeMeters of the source portal and player at trigger crossing and remain near the source until transfer. Other standing livestock remains excluded. A waiting animal remains stopped at its destination with its native patrol anchor translated to the new location. Native stay/patrol can include local wandering; wait is not a physics freeze. Follow or wait must be explicitly requested again for a later trip. Expiry, changed following or excessive movement cancels waiting consent.

Unmodified clients consume unknown slash commands locally, so `/follow`, `/stay` and `/wait` cannot be installed by a server-only module. Native `/comehere`, `/nonono` and `/wave` emotes provide reliable replicated input for follow, stay and wait respectively. Wave affects only a nearby animal already associated with the sender. Normal chat retains native delivery constraints. Confirmed commands and received-command selection failures use the vanilla Player Message RPC to provide private HUD feedback; requests are rate-limited and no native toggle is blindly retried.

Exact adult prefabs: **Wolf, Boar, Lox, Asksvin, Hen and Moose**. Installed assets supply persistent ZNetView, Tameable, Humanoid, MonsterAI, position-synchronizing ZSyncTransform and root capsule colliders. Only Wolf exposes ordinary native follow interaction. Moose and Asksvin use horizontal capsules; clearance must respect the capsule axis, not assume every animal is wolf-shaped. Runtime component checks stop activation if an expected animal definition changes. Exclude juveniles, wild/dead creatures, current riders, spiritcaller/summoned variants, Skeleton_Friendly, nonliving Tameable objects and unknown prefabs. Accept finite uniform scales from 0.25 to 4 only. Saddles remain attached; a nonzero native saddle user excludes transport.

The vanilla `/comehere` emote selects the uniquely nearest eligible tame within CommandRangeMeters; two candidates within half a metre of the nearest distance are ambiguous. The vanilla `/nonono` emote stops up to sixteen of that player's eligible nearby following or bound waiting animals per command, without nearest-distance ambiguity. A fresh stop can cancel native saved following after reconnect; it grants no travel consent. Foreign followers/bindings and busy handoffs remain excluded. Repeat the command for more than sixteen associated animals. Follow and wait retain uniquely nearest selection. Selection uses the physical sender's current living character and unique native player name; supplied chat name/position grants no authority. Player.StartEmote writes native emote/emoteID fields. The controller requires a newly applied, higher-revision character packet from that physical owner and an increasing emote counter; initial/replayed state grants no consent. Ordinary Wolf Command RPCs and normal-chat `!follow`/`!stay` are also accepted when routed through the server. Owner-local wolf commands and solo chat can bypass server routing, so the emotes are the reliable input path. Native Tameable.RPC_Command switches MonsterAI's target and saves the player's name. Unlike the client Interact check, that native handler does not require m_commandable, enabling these explicit follow/stay commands with unmodified clients. No animal recreation or commandability field override is needed.

Commands are sent once to an assigned native owner; unowned animals wait for native assignment. Native Command is a toggle, so a request is never blindly retried. Saved follow state must confirm the expected result within five seconds. `/comehere` or received `!follow` on a tame already following the same uniquely named player refreshes consent without toggling it. Another player's follower is never automatically reassigned. Native chat remains visible; confirmed results appear in server logs.

Bindings contain physical peer identity, current character ID, animal ID, name and consent time. No travel association is reconstructed from saved names at startup. A fresh authenticated follow/wait request may deliberately associate an animal already following that uniquely named player. Disconnects, character replacement, ambiguous names, name/follow changes and expiry invalidate bindings. FollowConsentSeconds limits travel consent, not native following duration. Reserving an animal consumes consent for one traversal; another traversal requires a fresh command. Standing livestock is never selected merely because it is near a portal.

## Server-controlled follow spacing

Native Character.GetHealth uses maximum health when its saved health field is absent; Character.Awake deliberately removes that field at full health. Player and tame eligibility accept this native representation without writing an invented health value. Explicit nonfinite/nonpositive saved health and native death remain ineligible. This rule also applies to stop commands addressing saved followers after reconnect. Transfer diagnostics distinguish omitted health from a saved value; relocation preserves the original representation.

FollowSpacingEnabled defaults true. After a fresh confirmed follow request, TameTravel may retain the original animal under server ownership to apply configurable follow spacing with unmodified clients. This is separate from portal consent: expiry consumes no animal and does not terminate established spacing. Stay/wait, changed following, death, riding, invalid player identity, disconnect, more than thirty-two metres separation, portal reservation, missing context or module disposal releases the spacing session. No session is reconstructed at startup. A confirmed following portal transfer requests a new spacing session without granting another trip.

FollowStopDistanceMeters defaults four metres and FollowResumeDistanceMeters five. Measure horizontal root-to-root distance, avoiding the native three-dimensional stair-height condition. Effective stop distance is at least the scaled horizontal capsule extent (including offset), the player's capsule extent and one metre of clearance. Effective resume is at least effective stop plus one metre. Stop/resume hysteresis avoids repeated movement changes near the boundary. Patch only BaseAI.Follow for leased, explicitly commanded animals; native combat, damage, feeding and ordinary physics continue. Use the native MoveTo with the effective stopping distance and walking on final approach. This is movement intent, not forced relocation or a physics freeze.

Use the existing source-record drain and ordered echo before simulation starts. Prepare native terrain and collision/character context within forty-eight metres; retain the follower and its actual player instance without claiming the player or surrounding objects. Start at most one context refresh per controller pass, rotating sessions, and refresh a ready session no more than once per second; a refresh is valid for three seconds. Suppress follower processing and freeze its body while draining or while context is unavailable. Release after ten seconds without a ready context. MaxControlledFollowers defaults eight globally (range one to sixteen); capacity refusal preserves native following and requires another explicit follow request to request spacing again. The combined ownership lease cap remains sixty-four. Riding requests release the lease before native control handling; other active-session object RPCs route to the server owner, while client record/destruction writes remain fenced. An animal still draining or paused for missing context cannot be reserved for a portal or receive another module command. Portal reservations release established spacing before their independent transfer protocol. Cleanup restores body state and relinquishes only owned animal records.

Normal output reports named spacing activation/release and capacity/context/handoff failures; Debug reports bounded acquisition, stop/resume, distances, owner and context evidence through the existing shared feature sample budget. Normal output does not repeat individual movement decisions.

## Portal traversal

Only player-built **portal_wood** and **portal_stone**, at unit scale, qualify. Require the native trigger box, nonempty matching tags, reciprocal connection IDs and outdoor endpoints at least twenty metres apart. Source observations use the prefab's child geometry, expanded for the native player capsule. Accept a fresh owner observation inside that trigger, including a player already inside when consent is confirmed, or an outside-to-inside/intersecting segment no longer than twelve metres with a gap no greater than two seconds. Leaving the trigger alone is not a new witness. Across a longer stationary update gap, a fresh point may establish inside-trigger presence without interpolating the missing path, provided the observed displacement remains within twelve metres. Multiple matched portal triggers invalidate source selection. A teleport-sized jump alone never authorizes travel.

Capture positions only after newer native player data has successfully applied from that character's physical owning peer. Retain up to thirty-two ordered revision/position/time observations per player between controller passes; duplicate revisions are ignored. Expensive scanning and reservations stay outside the networking callback. A rotating controller pass drains these observations in order, so a source point is not overwritten by a later destination update before evaluation. Source evidence must be at most two seconds old and cannot precede the binding's consent. Overflow discards incomplete history, cancels an active journey and resets the baseline; no historical jump is reconstructed. Query/filter native portal sectors at most once per processed player per pass and reuse the result for the bounded history. Arrival requires a fresh accepted owner observation at the linked exit. Timeouts, current destination clearance and ordering echoes continue during stationary packet gaps without inventing arrival.

Process historical source evidence before evaluating follower separation against the player's latest position. A matching linked exit observed less than two seconds after the source witness waits for a later accepted update; it is not classified as movement outside both endpoints. This accommodates a source witness received late in the native teleport wind-up without shortening the existing two-second arrival or eight-second readiness gates.

At entry reserve at most MaxFollowersPerTraversal confirmed followers or explicitly portal-waiting animals within FollowerRangeMeters of both the player and source portal. Snapshot both portal IDs, transforms, links and tag; recheck throughout the journey. First arrival must occur two seconds or later, within TravelWindowSeconds, at the native destination exit: within three horizontal metres and four vertical metres. Leaving the source without matching arrival cancels the journey. Require at least eight seconds since entry, two seconds of continued arrival observation within eight metres, a current peer reference position within four metres of the character and an authenticated native ping echo. The player must remain within eight metres while followers transfer. A journey ends at most TravelWindowSeconds plus thirty seconds after source entry.

Observed incoming RPC_TeleportTo/RPC_TeleportPlayer, server-side Player.TeleportTo and Chat.TeleportPlayer calls cancel matching journeys. Native player travel and its client-owned inventory checks are preserved. Server-observable endpoint evidence remains the approved policy; shared limitations describe indistinguishable owner-local administrative moves and client loading.

## Placement and transfer

Prepare native destination zones, saved terrain modifications and nearby scene colliders. Missing definitions, terrain or instances postpone placement. Use the actual scaled capsule, its native orientation and conservative player/creature exclusions. Search sixteen radial positions in front of the destination. Require dry ground at least half a metre above native water, normal.y >= 0.8, no lava, no solid overlap and a footprint with ground height variation no greater than half a metre. Reject elevated floors, water placements and positions more than twenty-two metres from the exit. Nearby recorded creatures count as obstacles even without a loaded server instance. Subsequent placements exclude already moved followers. Failed placement leaves that animal at its source.

Move the **original ZDOID**, never clone, destroy or recreate an animal. Keep all unrelated fields, including health, tame state/progress, name/author, level, saddle, feeding, breeding and custom data. Change position, rotation, native transient velocity fields and a completed-transfer timestamp. Translate saved native spawn/patrol spatial anchors by the relocation delta, preserving their relative offsets; waiting animals establish their new native patrol point at placement. Reset a loaded server instance's path, body and transient ground/fall state. Ordinary Character.TeleportTo does not move animals; native ZSyncTransform can move nonowners and initialize a new owner from the same record's position/velocities.

Each short transaction fences ownership and reserves the original ID. Revoke source ownership and explicitly send native ZDOData with a strictly newer ownership revision and wire data revision zero. Native RPC_ZDOData changes the existing client record's owner without overwriting its newer cached payload, and records zero as the server-known revision. Send native RequestZDO: its forced-send list then passes ShouldSend for a nonzero client revision, returning the full cached animal state even after ownership has ceased. Also send Game RPC_Ping on that same reliable connection. Require both the authenticated RPC_Pong ordering barrier and a successfully applied record returned by that previous physical owner showing the new server ownership revision. While draining, accept its newer native payload with server ownership retained. Only after both observations reject stale source writes. If a returned cache is absent, repeat the ownership/request barrier after two seconds, within the original ten-second phase limit; no animal moves on a timeout. Pause reserved server Character and its Humanoid override, MonsterAI, Tameable, Procreation and ZSyncTransform processing before handoff. Humanoid performs owner equipment/attack work before calling Character, so both entry points are covered. Retain an existing original scene instance through native create/remove lists; record-only sources are not instantiated at an unprepared source. After placement the native scene may create/retain the original record at its prepared destination. Reject client destruction and other animal interactions during the reservation. The forced native return reconciles persistent fields still queued on the former owner; private state absent from its native record is unavailable.

After safe placement, explicitly publish the same record to the destination player and require another ordered echo. Wait at least half a second before handing ownership to that player. Require a higher-revision packet from that exact physical peer, with matching assigned ownership and position within twelve metres of placement. Only successful native application of that update confirms resumed destination simulation. Retain the fence another two seconds before release. Reassert native revisions against late rejected records rather than allowing them to overwrite the moved animal. ForceSendZDO queues publication; it is never treated as an acknowledgement.

Failure before movement cancels relocation. Interruption afterward leaves the single original animal at its recorded destination and reports separately whether ownership was confirmed. It does not recreate the source or retry a consumed traversal. Each phase times out after ten seconds. Cleanup relinquishes server ownership or leaves the assigned destination owner to native reassignment.

## Persistence, settings and performance

Native world saves persist the original animal, transfer stamp and location together. No separate animal-copy journal exists. Restart invalidates all consent, trigger observations and transactions; no old journey is replayed. Native world rollback determines the restored location and state. See [shared save/delivery limitations](../limitations.md#tametravel).

| Setting | Default | Rationale and range |
| --- | --- | --- |
| Enabled | true | Requested default; independent module. |
| DebugMode | false | Normal outcomes remain visible; detail is optional. |
| CommandRangeMeters | 8 | Deliberate nearby selection; 2..12. |
| FollowSpacingEnabled | true | Apply server-owned spacing after explicit follow; independently switchable within TameTravel. |
| FollowStopDistanceMeters | 4 | Horizontal stop distance; 3..12, enlarged for body clearance. |
| FollowResumeDistanceMeters | 5 | Horizontal resume distance; 4..16, at least effective stop plus one. |
| MaxControlledFollowers | 8 | Global simulated follower cap; 1..16. |
| FollowerRangeMeters | 20 | Source-local followers; 5..32. |
| FollowConsentSeconds | 300 | Fresh consent for one traversal; 30..1800. |
| TravelWindowSeconds | 30 | Bounded distant travel/loading observation; 15..60. |
| MaxFollowersPerTraversal | 8 | Bounded reservations; 1..16. |

Use the central loader and shared hidden debug-suppression policy. Restart applies changes. Poll at 0.25 seconds, processing at most eight of sixty-four ready players per pass. Dense rosters may exceed the accepted observation-age/history bounds and defer travel safely. At most 512 bindings/reservations, 64 player samples/journeys with thirty-two queued owner observations each, 64 transactions, 512 native ordering barriers and 1024 deduplicated routed-message IDs are retained. Each nearby-sector query rejects over 8192 records rather than truncating safety evidence. Start at most one transaction and run at most one sixteen-candidate placement search per pass. Query native nearby sectors, never the entire world. Scene context retains at most 8192 records and expires unused inclusions after ten seconds. Commands are rate-limited per peer to one observed message per second; duplicate routed copies do not refresh consent. Capacity or uncertain state withholds work.

## Player-service integration

Follow the [required hookup](../architecture.md#required-feature-hookup). Plugin injects its PlayerServices; TameTravel owns one presence subscription and its controller owns routed-message observation, native hooks, consent, traversal, context, bounded server-controlled following and transaction authority. No AFK activity lease is acquired. Enabled, shared exact-version compatibility, joined presence and native ZNet/ZDOMan/ZNetScene/ZoneSystem/ZRoutedRpc readiness are separate gates. False/unknown presence disposes gameplay resources before pause acknowledgement; the presence registration remains. World replacement, failure and shutdown invalidate observations and release resources. There is no offline gameplay exception. Cleanup attempts all owned releases and propagates errors without disabling unrelated modules.

## Logging and acceptance criteria

Selection diagnostics share a further eight-record-per-minute allowance: scope counts and at most three nearest supported-animal samples per request, including rejected candidates. Samples identify player/peer, animal/prefab, eligibility reason, distance/range, saved-health presence/value, tame state, saved following and owner. Expensive candidate ordering runs only under the effective Debug policy. These samples cannot consume the command receipt/rejection allowance.

Fresh applied emote changes, recognized requests and concrete selection/actor/rate-limit rejection reasons are Debug command evidence, bounded to thirty-two records per minute. Actor-gate changes use a bounded sixty-four-player reason cache. No saved emote or follow name alone authorizes travel.

Reserve sixteen Debug records per minute for traversal entry/arrival/readiness, source and follower gate reasons, consent loss, placement waits, cancellations and reservation endings. Movement/scope samples have a separate two-record allowance so repeated stop/resume changes cannot exhaust traversal evidence. Together with eight selection records and one controller plus one movement timing report, recurring output is bounded to sixty records per minute. Unchanged gate reasons deduplicate by player/stage/reason/portal/animal for five minutes in a 256-entry cache; semantic transitions retain each occurrence within the stream cap. Omitted traversal samples are counted in the next permitted evidence record. Fields include player/peer, source/animal IDs, observed positions, sample age/gap, range limits, consent order/age, and the expected exit as appropriate. Destination distance, overall traversal timeout, missing owner samples, out-of-range animals, altered following and wait-area movement have separate reasons. Placement waits distinguish terrain, prefab, retained-context capacity, collision instances and absence of a safe ground position. Cancellation propagates its original reason to every affected animal reservation.

Normal output includes one named notice when a detected journey ends before any relocation, and the traveler receives a private HUD explanation requiring fresh follow followed by optional wait. A consumed waiting association cannot be rebuilt from its now-empty native following field by wait alone. Source detection gives private destination-wait guidance; completion confirms arrival or distinguishes recorded relocation from unconfirmed destination ownership. These are per-attempt outcomes, not periodic polling notices.

Normal output includes lifecycle/failures, one named result per confirmed animal follow/stay change and one named moved-count result per completed journey. Relocated animals without destination-owner confirmation are distinguished. Empty/unchanged passes are silent. Different player/journey results retain their identities. Optional Debug entry/transaction/scope evidence shares a sixteen-sample per-minute budget; optional formatting follows effective shared suppression.

- Valid traversal moves only its reserved confirmed following/waiting animals, retaining original IDs and unrelated persistent native data.
- Standing livestock, stale consent, duplicate names, changed characters, retagged links, interiors, respawns and observed competing teleports cannot authorize travel.
- Unsafe/unready placement, riders, missing replication and timeouts cannot consume or duplicate an animal.
- Explicitly commanded followers use configured horizontal stop/resume thresholds only while server ownership and scene context are established; riding and unsafe context release spacing without copying an animal.
- Native manual commands remain usable; requests, ordered delivery and resumed-owner observation are distinct outcomes.
- Restart, pause, ownership transitions and failure cannot replay a previous journey; unrelated modules may all be disabled.
- Supported environment values appear only in [server setup](../server-setup.md#supported-environment).

## Comparable source

Its commandability field overrides require client instance initialization. [Historical TeleportEverything](https://github.com/KPro1982/TeleportEverything-Old/blob/cbc64e57ec2353812f1921c7bba97ca9bcfde96b/TeleportEverything.cs) patches local-player teleport execution and supplies no dedicated-server proof. Installed native execution, assets and ownership paths determine HeimKit's implementation.

Optional bounded cancellation samples identify changed portal/actor evidence, arrival timeout, movement outside matched endpoints and destination-clearance/traversal timeout. Transfer completion samples include original animal ID, phase, source-state barrier result, previous/current owner and native revisions, separating relocation from confirmed destination ownership. Placement caches static collider requirements and collects creature obstacles once per search; the sixteen placement probes reuse that bounded snapshot.

Optional follow-movement timing aggregates the changed BaseAI.Follow path, including its synchronous native MoveTo call, once per minute under effective debug. It excludes other AI/physics and deferred native work.

Optional controller-pass timing reports duration_avg_ms and duration_max_ms at most once per minute for nonempty scope. Collection follows effective debug policy and includes synchronous controller processing only; see [shared measurement limitations](../limitations.md).

Reservation-end diagnostics capture a controller-owned snapshot before cleanup, then format that snapshot after release. Include exact validation/cancellation reason, record identity, owner/revisions, position, saved following, health, tame/rider state, phase age and ordering-echo result. Owner-after-release is not used as failure evidence. Missing/replaced records remain unknown.
