# TameTravel specification

## Proposed general rule for linked outdoor portals

Every tamed animal and every player-summoned creature in Valheim is in scope for follower travel. Either an authenticated `/comehere` that establishes following or a native follow order whose resulting state the host can verify qualifies the creature. The player can initiate either from a vanilla or HeimKit client. Once the host verifies the follower, a second command is unnecessary. A stay or changed follow target cancels following eligibility. The separate one-trip wait order retains its existing semantics.

The world host runs TameTravel in solo, Start Server and dedicated play. Attribute the traveller to the current living character. For ordinary animals verify tame state and follow target, resolving name-based following only for a unique player. For summons also verify the original player summoner across simulation-owner changes. Preserve native summon limits and lifetimes. Record each species' native command support, replicated follow and caster evidence, body and placement requirements before enabling its integration. Where native follow is unavailable, assess the HeimKit emote path separately. A nearby juvenile without an established follow relationship does not inherit an adult's trip.

Use the existing bounded source search, reciprocal portal validation, ownership handoff and destination placement checks. Recheck each original creature's identity and eligibility before moving it. The host's debug trace should tie acceptance or rejection to the traveller, creature ID, follow evidence, summon attribution where applicable and outcome. Acceptance covers both command paths, multiple followers, another player's follower and an order revoked during transit. The implementation sections below describe current species coverage.

## Behavior and native feasibility

Preserve each ordinary tame's native player interaction. For a natively commandable tame, Valheim's normal interaction can stop an existing live follower even when another player gives the command. A subsequent interaction while it has no follow target can start following the caller. HeimKit-added commands protect a connected player's active follower. Once that player releases the animal or their disconnect is confirmed and the prior association clears, another player may request follow. A change of simulation owner does not release the association. Dead Raiser travel continues to require the original summoner.

TameTravel accompanies a player's validated traversal between linked vanilla portals outside native interiors (dungeons) with that player's explicitly following or portal-waiting ordinary tames. It never teleports the player, changes native player portal restrictions or performs general distance catch-up. Enabled defaults true; each module remains independent.

The installed client and dedicated-server portal methods execute normal travel on the owning client. TeleportWorldTrigger requires Player.m_localPlayer; TeleportWorld.Teleport checks restrictions and calls Player.TeleportTo without a portal-use RPC. Player.UpdateTeleport publishes its changed transform through ordinary replication. For a remote player, the contract is observed traversal: fresh authenticated following, source-trigger crossing, an unchanged reciprocal portal pair, corresponding arrival and readiness constraints. The host has direct access to the native call sequence. Shared observation qualifications belong in [limitations](../limitations.md#tametravel).

The public-map marker is another position consumer: Player.LateUpdate sets ZNet's reference position; ServerSyncedPlayerData sends it every two seconds; PlayerList distributes public positions. Minimap.UpdatePlayerPins animates the marker toward updates at 200 metres per second. That animation does not describe a physical path through the world. TameTravel samples actual character ZDO positions and does not require public map visibility. RequestZDO, private teleport flags and local PortalsUsed statistics supply no additional causal portal event. Taking player ownership or replacing player travel would interfere with native controls/inventory restrictions and is excluded.

### Player-hosted worlds

The host uses the same command, binding, tame-selection and safe-placement rules. Native chat, successful supported emotes and native tame commands are attributed to the current local character through Core’s world actor identity. Guests in a Start Server world continue to use the authenticated remote observation paths. The host receives private HUD messages directly.

Host entry is witnessed only when `TeleportWorld.Teleport` calls the local player’s `Player.TeleportTo` with the linked destination and the native method accepts it. The local journey retains the source and reciprocal destination identities. A finishing `Player.UpdateTeleport` must leave the same living character at that exit. A changed pair, competing teleport, expired window, death or world replacement releases pending work. Placement requires native destination readiness and the existing collision and clearance checks. Host arrival reuses the original animal record and keeps native host ownership at commit. A guest-owned source still needs its ordered state drain, or waits while its owner is unavailable within the journey deadline. Remote arrival retains the existing destination-owner handoff. Disablement and world teardown remove the local hooks and release reservations.

### Ordinary tames at dungeon doors

A current confirmed follow binding can authorize the original living, unridden tame on either side of a native dungeon crossing. Recheck the binding and native follow name at commit. Ignore waiting animals. Use the original scaled capsule and visible body bounds for doorway width, height and depth. Check loaded terrain and static clearance at both doorway approaches, a supported collision-free landing and room to move away. Bodies wider or taller than the player capsule must clear the doorway plane itself. Exclude Lox at the Infested Citadel. A Troll Cave still requires measured clearance. A wide interior alone cannot authorize a large tame. Keep this independent of the staff summon switch. Preserve ordinary outdoor portal selection and handoff.

### Dead Raiser summons

In a private world or for the Start Server host, record the local player profile ID on the original persistent Skeleton_Friendly ZDO during the Dead Raiser's native spawn command. The installed StaffSkeleton primary attack references staff_skeleton_spawn directly. Attack.FireProjectileBurst passes its character and weapon to SpawnAbility.Setup. Its spawn coroutine selects the skeleton level and weapon-quality instance limit before issuing Command. The simulation peer can subsequently change. The native saved follow name can change or be cleared, and the ZDO ID's allocating session identifies a process rather than a player profile. Neither establishes who originally cast the staff.

A witnessed, accepted linked outdoor portal or successful native dungeon Teleport.Interact opens a bounded journey for the local summoner. Discover dungeon gateways from active native Teleport components and their configured destinations. A gateway must cross between exterior and interior space. Eligibility is independent of location prefab name, hover text and whether the destination points back. Evaluate each direction separately and recheck the original source, destination and landing transform through completion. Check both directions, the expected target, successful native teleport completion, the same living player and loaded destination floor. Require the caster stamp, saved following and live AI target at departure. Track original record identities independently of gateway identity. For a locally simulated host follower, retain the source authority revision through commit. For a host follower simulated by a guest, use the same ordered source drain as a remote crossing. Abandon an individual if its record, health or following becomes ineligible. Temporarily defer only the reserved follower's native distance-unsummon check while the crossing resolves. Death, logout and native count enforcement remain effective. Move the same record onto a supported, unobstructed floor near the arrived player. Each new crossing selects current followers again. Ordinary tames use their own confirmed follow binding for dungeon travel.

For a vanilla guest on a dedicated or Start Server host, attribute a newly received persistent friendly skeleton to the profile of the joined character on the sending connection only when that connection also allocated the skeleton ID and supplied its initial owner state with the native staff limit. Preserve the association independently of later simulation ownership. Select by caster, current native follow name and source proximity. A server-enabled SummonTravel switch defaults on and can be disabled independently of ordinary tame travel.

Use one pending crossing per physical traveller and character and one ownership reservation per original skeleton. At a native dungeon doorway or linked portal, drain the prior simulator before its distance-unsummon can race the trip. Require observed arrival at that specific exit followed by fresh owner-replicated horizontal movement away from the fixed teleport target while the player remains nearby. A tentative destination sample alone never commits. Reject rollback, competing travel, expired evidence, changed links, lost following, death and disconnect. Check host floor and body clearance at arrival and hand the original record to the traveller's peer. The player-host’s own crossing can use its native completion witness. Normal output groups successful summon relocations by traveller and crossing. Debug identifies the traveller, original record and position of each summon moved for correlation with the optional local client trace. Apply the nearby record limit to summon and gateway candidates at departure. At arrival apply it to nearby collision context, dungeon generators and relevant terrain records. An oversized relevant set defers the transfer as a whole. Unrelated base pieces outside the landing area do not count. For linked portals the host can observe entry across a short, recent segment between source samples. Once arrival is confirmed within ten metres, the player may move within the ordinary portal landing radius on the same side of the gateway. Allow thirty seconds from confirmation for placement and handoff. Host Debug identifies each released original record, its transfer phase and the last unmet condition.

## Supported objects and following

Normal chat commands are `!follow`, `!stay` and `!wait`; `!tame` requests concise command help. Follow grants session-scoped portal permission and starts native following. One authenticated follow command covers successive validated portal trips; the animal resumes following after each confirmed destination handoff without a wait command. Stay stops following and cancels consent. Wait requires this player's existing confirmed association or a fresh authenticated request addressing an animal currently following that uniquely named player, stops native following and retains fresh single-trip consent while the animal stays within FollowerRangeMeters of its waiting position. Waiting animals must also be within FollowerRangeMeters of the source portal and player at trigger crossing and remain near the source until transfer. Other standing livestock remains excluded. A waiting animal remains stopped at its destination with its native patrol anchor translated to the new location. Native stay/patrol can include local wandering; wait is not a physics freeze. Active following retains its permission across later trips; optional waiting consent is consumed by reservation and requires a fresh follow/wait command for another trip. Expiry, changed following or excessive movement cancels waiting consent.

Unmodified clients consume unknown slash commands locally, so `/follow`, `/stay` and `/wait` cannot be installed by a server-only module. Native `/comehere`, `/nonono` and `/wave` emotes provide reliable replicated input for follow, stay and wait respectively. Wave affects only a nearby animal already associated with the sender. Normal chat retains native delivery constraints. Confirmed commands and received-command selection failures use the vanilla Player Message RPC to provide private HUD feedback; requests are rate-limited and no native toggle is blindly retried.

Ordinary tame commands accept these exact adult prefabs: **Wolf, Boar, Lox, Asksvin, Hen and Moose**. Installed assets supply persistent ZNetView, Tameable, Humanoid, MonsterAI, position-synchronizing ZSyncTransform and root capsule colliders. Only Wolf exposes ordinary native follow interaction. At a linked outdoor portal the host also accepts an adult wolf whose current replicated follow target matches the uniquely identified traveller. This authorization is scoped to the witnessed trip. Reuse the bounded nearby search to observe approaches, check both source ranges, and recheck follow state and conflicting orders before placement. A pending stop takes precedence. Host debug reports the wolf ID, owner, follow target and entry decision. This path creates no persistent command binding and does not extend to cubs or dungeon doors. Observe a native toggle for ordinary travel consent only when its prefab supports pet commands and the native call requests a player message. Silent saved-follow restoration leaves existing consent alone. Explicit HeimKit orders keep their own binding and confirmation path. Moose and Asksvin use horizontal capsules; clearance must respect the capsule axis, not assume every animal is wolf-shaped. Runtime component checks stop activation if an expected animal definition changes. From those commands, exclude juveniles, wild/dead creatures, current riders, spiritcaller/summoned variants, Skeleton_Friendly, nonliving Tameable objects and unknown prefabs. Accept finite uniform scales from 0.25 to 4 only. Saddles remain attached; a nonzero native saddle user excludes transport.

The vanilla `/comehere` emote selects the uniquely nearest eligible tame within CommandRangeMeters; two candidates within half a metre of the nearest distance are ambiguous. The vanilla `/nonono` emote stops up to sixteen of that player's eligible following or bound animals within thirty-two metres per command, without nearest-distance ambiguity. A fresh stop can cancel native saved following after reconnect; it grants no travel consent. Followers of connected players and their active bindings remain excluded. A fresh authenticated follow request may reclaim an absent player's stale saved following only after the stop handshake clears it. Loading/respawning transport peers remain protected, and unknown presence never authorizes reclamation. Stop takes priority during follow acquisition and portal handoffs, cancelling permission and releasing spacing control before native stay confirmation. Repeat the command for more than sixteen associated animals. Follow and wait retain uniquely nearest selection. Selection uses the physical sender's current living character and unique native player name; supplied chat name/position grants no authority. Player.StartEmote writes native emote/emoteID fields. The controller requires a newly applied, higher-revision character packet from that physical owner and an increasing emote counter; initial/replayed state grants no consent. Ordinary Wolf Command RPCs and normal-chat `!follow`/`!stay` are also accepted when routed through the server. Owner-local wolf commands and solo chat can bypass server routing, so the emotes are the reliable input path. Native Tameable.RPC_Command switches MonsterAI's target and saves the player's name. Unlike the client Interact check, that native handler does not require m_commandable, enabling these explicit follow/stay commands with unmodified clients. No animal recreation or commandability field override is needed.

Follow is sent once to an assigned native owner and confirmed from saved following. Stop and wait use an idempotent server-owned stop handshake instead of the native toggle: drain any previous owner, clear the server live AI target and saved following, establish a patrol anchor at the animal, and refresh ready clients' cached copies of this one animal. Core sends targeted native DestroyZDO cache-removal messages followed by the same authoritative record ID; the server never destroys or replaces the world animal. Require ordered client echoes and at least half a second for scene refresh before releasing ownership and confirming stay. An ownership/cache timeout reports unconfirmed stay. Another player's changed saved following cancels cleanup. An explicit reclaim first stops the verified absent player's old following, rechecks that player remains absent, and only then sends one fresh follow request for the authenticated requester; pending reclamation grants no portal permission. A fresh stay preempts that request without starting following. Follow requests remain blocked while that animal is stopping.

Bindings contain local character identity or physical peer identity, current character ID, animal ID, name and consent time. No travel association is reconstructed from saved names at startup. A fresh authenticated follow/wait request may deliberately associate an animal already following that uniquely named player. Disconnects, character replacement, ambiguous names, name/follow changes and expiry invalidate bindings. FollowConsentSeconds applies only to optional waiting consent. Confirmed follow bindings have no timer while the same physical player session, character, unique name and native saved following remain valid. Reservation retains follow bindings but consumes optional wait bindings; a transfer timeout does not by itself revoke unchanged follow permission. Pending stop/wait, changed following, invalid animal/actor identity, disconnect and cleanup revoke follow authority. Standing livestock is never selected merely because it is near a portal.

## Session cleanup and startup recovery

Disconnect, character replacement and session cleanup revoke travel permission and enqueue stopping independently of whether the animal has an active spacing lease. A stop already queued survives removal of the command binding and waits for a portal reservation to release. Last-player departure and orderly controller shutdown clear saved following and local native targets before final ownership release; available clients receive same-ID cache refreshes.

Fresh follow associations stamp server-owned provenance on the animal's original persistent record. The bounded active registry reasserts those keys immediately before native PrepareSave snapshots, because client extra-data payloads can replace server-added fields. Dedicated-server ZDO.Load/LoadOldFormat hooks clear marked previous-session following while records are loading from disk, before players receive them. This is intentional offline access cleanup, independent of the presence-gated gameplay controller; it neither scans the world nor installs a hot Deserialize hook. Recovery remains conditional on TameTravel being enabled and compatible. Normal output combines recovered records since the last report; individual record identities and client-refresh counts accompany stop results. Failures remain visible without Debug.

Older builds did not stamp provenance. On loading an unmarked supported boar, lox, asksvin, hen or moose, clear a nonempty saved follow name: these animals have no vanilla follow command. Unmarked wolves retain their native following; a fresh authenticated stay can clear them. Never clear a marked record that now follows a different player, an unsupported object, dead animal or occupied saddle. Recovery changes neither health, tame state, name, saddle nor the authoritative record identity.

## Server-controlled follow spacing

Native Character.GetHealth uses maximum health when its saved health field is absent; Character.Awake deliberately removes that field at full health. Player and tame eligibility accept this native representation without writing an invented health value. Explicit nonfinite/nonpositive saved health and native death remain ineligible. This rule also applies to stop commands addressing saved followers after reconnect. Transfer diagnostics distinguish omitted health from a saved value; relocation preserves the original representation.

FollowSpacingEnabled defaults true. After a fresh confirmed follow request, TameTravel may retain the original animal under server ownership to apply configurable follow spacing with unmodified clients. Follow spacing and portal authorization share the explicit follow association but retain independent ownership/context limits. Optional wait-consent expiry does not control an active follow association. Stay/wait, changed following, death, riding, invalid player identity, disconnect, more than thirty-two metres separation, portal reservation, missing context or module disposal releases the spacing session. No session is reconstructed at startup. A confirmed following portal transfer requests a new spacing session only while the same active follow authorization remains; that association also authorizes later validated trips.

FollowStopDistanceMeters defaults four metres and FollowResumeDistanceMeters five. Measure horizontal root-to-root distance, avoiding the native three-dimensional stair-height condition. Effective stop distance is at least the scaled horizontal capsule extent (including offset), the player's capsule extent and one metre of clearance. For Lox specifically, effective stop is also at least six metres to allow room beyond its small native collision capsule; effective resume is at least eight metres and effective stop plus two metres. Other animals retain effective resume at least effective stop plus one metre. Larger configured distances and scaled physical extents still apply. Stop/resume hysteresis avoids repeated movement changes near the boundary. Patch only BaseAI.Follow for leased, explicitly commanded animals; native combat, damage, feeding and ordinary physics continue. Use the native MoveTo with the effective stopping distance and walking on final approach. This is movement intent, not forced relocation or a physics freeze.

Use the existing source-record drain and ordered echo before simulation starts. Prepare native terrain and collision/character context within forty-eight metres; retain the follower and its actual player instance without claiming the player or surrounding objects. Start at most one context refresh per controller pass, rotating sessions, and refresh a ready session no more than once per second; a refresh is valid for three seconds. Suppress follower processing and freeze its body while draining or while context is unavailable. Release after ten seconds without a ready context. A session also ends when the animal is more than thirty-two metres from its player. While that animal keeps the same saved follow name and the same player character stays connected, spacing is requested again once it is back within sixteen metres; portal reservation, stop handshakes, stay/wait and any player, record or follow-name change forget it. At most sixty-four such animals are remembered. MaxControlledFollowers defaults eight globally (range one to sixteen); capacity refusal preserves native following and requires another explicit follow request to request spacing again. The combined ownership lease cap remains sixty-four. Riding requests release the lease before native control handling; other active-session object RPCs route to the server owner, while client record/destruction writes remain fenced. An animal still draining or paused for missing context cannot be reserved for a portal or receive another follow/wait command; stay cancels that control. Portal reservations release established spacing before their independent transfer protocol. Cleanup restores body state and relinquishes only owned animal records. Stay or wait detaches the spacing session into the shared stop handshake; it does not release the ownership fence before cached client targets have been reset.

Normal output reports named spacing activation/release and capacity/context/handoff failures; Debug reports bounded acquisition, stop/resume, catch-up, distances, owner and context evidence through the existing shared feature sample budget. Each session end is a follow-topic Debug record naming its reason, drawn from the six-per-minute traversal allowance. Normal output does not repeat individual movement decisions.

## Portal traversal

Only player-built **portal_wood** and **portal_stone**, at unit scale, qualify. Require the native trigger box, matching raw tags (including blank tags, as supported by native Game.ConnectPortals), reciprocal connection IDs and endpoints outside native interiors, at least twenty metres apart. Portals inside ordinary above-ground buildings qualify. Source observations use the prefab's child geometry, expanded for the native player capsule. Accept a fresh owner observation inside that trigger, including a player already inside when consent is confirmed, or an outside-to-inside/intersecting segment no longer than twelve metres with a gap no greater than two seconds. Leaving the trigger alone is not a new witness. Across a longer stationary update gap, a fresh point may establish inside-trigger presence without interpolating the missing path, provided the observed displacement remains within twelve metres. Among crossed triggers, select a uniquely usable reciprocal pair; a neighboring unlinked or ineligible destination does not mask that pair. Multiple usable crossed pairs, or multiple crossed triggers with no uniquely usable pair, remain ambiguous and withhold travel. A teleport-sized jump alone never authorizes travel. If a uniquely witnessed source has an unassigned link, a missing destination record or a nonreciprocal link, retain one source witness per player for at most six seconds while native link updates settle. Snapshot the original source record, transform, raw tag, accepted owner observation and any known destination ID; learn an initially missing target once, then reject changes. Retries perform direct native-ID lookups without world scans or tag-based target guessing. Retagging, moved/replaced sources, changed known links, incomplete position history, consent/session loss and observed competing teleports discard the witness. The player must remain near the source or have a fresh accepted position at that exact linked exit. Once links validate, use the original source observation and replay the accepted position through the unchanged arrival timing/readiness rules. Stale polling positions never establish arrival; no animal is reserved or moved solely on an unresolved witness.

Capture positions only after newer native player data has successfully applied from that character's physical owning peer. Retain up to thirty-two ordered revision/position/time observations per player between controller passes; duplicate revisions are ignored. Expensive scanning and reservations stay outside the networking callback. A rotating controller pass drains these observations in order, so a source point is not overwritten by a later destination update before evaluation. Source evidence must be at most two seconds old and cannot precede the binding's consent. Overflow discards incomplete history, cancels an active journey and resets the baseline; no historical jump is reconstructed. Query/filter native portal sectors at most once per processed player per pass and reuse the result for the bounded history. Arrival requires a fresh accepted owner observation at the linked exit. Timeouts, current destination clearance and ordering echoes continue during stationary packet gaps without inventing arrival.

Process historical source evidence before evaluating follower separation against the player's latest position. A matching linked exit observed less than two seconds after the source witness waits for a later accepted update; it is not classified as movement outside both endpoints. This accommodates a source witness received late in the native teleport wind-up without shortening the existing two-second arrival or eight-second readiness gates.

At entry reserve at most MaxFollowersPerTraversal confirmed followers or explicitly portal-waiting animals within FollowerRangeMeters of both the player and source portal. Snapshot both portal IDs, transforms, links and tag; recheck throughout the journey. Begin at most one source ownership drain per controller pass immediately after reserving animals at detected entry, before destination readiness; this pauses their source simulation during the player trip without issuing a native stay toggle or changing saved following. A drained source waits in phase one for independently authenticated destination readiness. First arrival must occur two seconds or later, within TravelWindowSeconds, at the native destination exit: within three horizontal metres and four vertical metres. Leaving the source without matching arrival cancels the journey. Require at least eight seconds since entry, two seconds of continued arrival observation within forty-eight metres, a current peer reference position within four metres of the character and an authenticated native ping echo. After the initial linked-exit arrival is authenticated, new animal acquisition, relocation and handoff allow the player to move within forty-eight metres of the destination exit, including outside a portal building. Initial arrival geometry and timing remain unchanged. A journey ends at most TravelWindowSeconds plus thirty seconds after source entry. After completion, block the relevant arrival trigger (or source trigger when nothing moved) until an accepted player position leaves it, preventing standing inside a portal from continually reserving return journeys.

Observed incoming RPC_TeleportTo/RPC_TeleportPlayer, server-side Player.TeleportTo and Chat.TeleportPlayer calls cancel matching journeys. Native player travel and its client-owned inventory checks are preserved. Server-observable endpoint evidence remains the approved policy; shared limitations describe indistinguishable owner-local administrative moves and client loading.

## Placement and transfer

With departure animals under observation, the client samples the floor beneath the traveller on arrival and again three seconds later if observation continues. The destination_floor event identifies the floor and overhead collider, their network IDs when available, the floor height above terrain, the vertical clearance at that point and the watched animal IDs. A missed upward probe reports its twelve-metre range.

Prepare native destination zones, saved terrain modifications and nearby scene colliders across a fifty-six-metre context. Missing definitions, terrain or instances postpone placement. Use the actual scaled capsule, its native orientation and conservative player/creature exclusions. Use the native destination rotation projected onto the ground plane as the facing that defines front, left and right. Search arcs centred on the traveller's position, restarting from the first arc when the traveller has moved more than one metre. The first arc lies at the animal horizontal extent plus 1.55 metres, just outside traveller clearance; later arcs step out a quarter metre for every animal, up to twelve metres. Spots along an arc are a quarter of the animal's width apart (half its horizontal extent), never closer than a quarter metre. Each arc runs from the traveller's right side across the front to the left side, then through the newly added ground behind the right side and then behind the left side. The covered span grows evenly from the front half on the first arc to a full circle on the last. The order is fixed, so the same surroundings give the same choice. Fallback square grid rings then align to the portal and interleave exit and traveller anchors; their spacing remains two to three metres according to animal size. Landings may lie on any side of the portal; the portal is an obstacle like any other piece. Unsupported near-vertical portal facing withholds placement. Keep landing points within forty-eight horizontal metres of the exit and ground within twenty-four vertical metres. Visit at most sixty-four candidates per controller pass, retaining the cursor and wrapping when complete. Placement allows thirty seconds after destination readiness; other transaction phases retain ten-second limits and the overall deadline still applies.

Require dry support at least half a metre above water, normal.y >= 0.8, no lava, no scaled-capsule solid overlap, 0.75 metres of padding from Default, static_solid, Default_small, piece and vehicle colliders, and nine footprint support samples. Padding excludes terrain and creatures, which have their own checks. The padded capsule is raised so its underside matches the unpadded capsule; its radius grows, and obstacles entirely above the unpadded body and its collision margin are excluded from the padding check. An overlapped padded landing moves by its summed horizontal penetration vectors plus five centimetres and is rechecked in full, up to three times; a thirty-two-collider overlap overflow or a zero push rejects it. Walkout sweeps keep the unpadded capsule. Support probes cast down to terrain from one metre above the higher of the requested walking level and terrain. They select the highest upward-facing piece below that origin, or terrain if there is none. Footprint probes use the selected support level and walkout steps follow the previous support level. That piece must be a low static structural slab, whether player-built or world-generated: non-comfort Piece, supporting static WearNTear, collider bounds at most 1.25 metres high (stone and marble floors included) and at least 0.5 metres across both horizontal axes, at any height within the existing exit bounds. When the highest surface is any other piece, the spot is rejected as `unsupported_surface` rather than placing the animal at terrain height beneath it. Furniture remains excluded. Ceilings and upper storeys can overhang a landing when the scaled body fits. Each probe uses a reusable thirty-two-hit buffer and withholds on overflow. Footprint heights must match the local support plane within half a metre. Nearby recorded creatures count as obstacles even without a loaded server instance. Subsequent placements exclude already moved followers. A landing also needs a clear walkout at least three metres long, enlarged to the animal's horizontal half-extent plus two metres. Try eight compass directions with support checks at intervals no greater than one metre, height changes consistent with the allowed slope and full scaled-capsule sweeps. Walkout roots remain within fifty-six metres of the exit. Each search shares sixty-four escape samples. When they run out before a candidate's walk-out check finishes, the next pass starts again at that candidate; a check that runs out after starting with the full budget counts as blocked.

For a Lox at a linked destination portal beneath a player-built roof, an open-air landing with body clearance and a walk-out can be used independently of a path through the house door. For other outdoor placements, require a full native HumanoidNoSwim route from the current traveller to the support point. This player-sized access check permits doorways without requiring the animal itself to fit through them. Native route endpoints must remain within one horizontal and one vertical metre of their requested positions; reject over 128 corners, routes over 96 metres or detours exceeding direct distance plus twelve metres. Sphere overlap and swept checks at 0.8 and 1.5 metres above every route segment recheck current static geometry and vehicles, preventing a stale route from crossing walls. At most four native route requests occur per placement pass. Once the player has arrived and the exit zone is loaded, a native route request from the player to the exit at most once a second, until destination readiness, starts that preparation early. The first unavailable route retains its candidate for up to four seconds to allow native asynchronous navigation preparation; all preparation remains inside the placement deadline. Unknown, blocked or unsupported routes defer placement. Failed placement leaves that animal at its source.

Move the **original ZDOID**, never clone, destroy or recreate an animal. Keep all unrelated fields, including health, tame state/progress, name/author, level, saddle, feeding, breeding and custom data. Change position, rotation, native transient velocity fields and a completed-transfer timestamp. Translate saved native spawn/patrol spatial anchors by the relocation delta, preserving their relative offsets; waiting animals establish their new native patrol point at placement. Reset a loaded server instance's path, body and transient ground/fall state. Ordinary Character.TeleportTo does not move animals; native ZSyncTransform can move nonowners and initialize a new owner from the same record's position/velocities.

Targeted native snapshots are sent by TameTravelReplication, which validates the same physical native ZDOPeer connection and mirrors its sent-data/owner revisions. Only after a successful reliable send, consume that animal's queued sector invalidation and force-send entry; preserve unrelated IDs and all queue entries on send failure. A direct moved snapshot already reindexes the client's record through native InternalSetPosition, so a later redundant invalidation must not follow it. Source-drain packets acknowledge their actual wire data revision zero, preserving native RequestZDO reconciliation. Per-peer sent metadata is not a rendering acknowledgement.

Each short transaction fences ownership and reserves the original ID. Source drain may start before player arrival; neither destination placement nor publication starts before readiness. Revoke source ownership and explicitly send native ZDOData with a strictly newer ownership revision and wire data revision zero. Native RPC_ZDOData changes the existing client record's owner without overwriting its newer cached payload, and records zero as the server-known revision. Send native RequestZDO: its forced-send list then passes ShouldSend for a nonzero client revision, returning the full cached animal state even after ownership has ceased. Also send Game RPC_Ping on that same reliable connection. Require both the authenticated RPC_Pong ordering barrier and a successfully applied record returned by that previous physical owner showing the new server ownership revision. While draining, accept its newer native payload with server ownership retained. Only after both observations reject stale source writes. If a returned cache is absent, repeat the ownership/request barrier after two seconds, within the original ten-second phase limit; no animal moves on a timeout. Pause reserved server Character and its Humanoid override, MonsterAI, Tameable, Procreation and ZSyncTransform processing before handoff. Humanoid performs owner equipment/attack work before calling Character, so both entry points are covered. Retain an existing original scene instance through native create/remove lists; record-only sources are not instantiated at an unprepared source. After placement the native scene may create/retain the original record at its prepared destination. Reject client destruction and other animal interactions during the reservation. The forced native return reconciles persistent fields still queued on the former owner; private state absent from its native record is unavailable.

After safe placement, explicitly publish the same record to the destination player and require another ordered echo. Wait at least half a second before handing ownership to that player. Require a higher-revision packet from that exact physical peer, with matching assigned ownership and position within twelve metres of placement. Only successful native application of that update confirms resumed destination simulation. Retain the fence another two seconds before release. Reassert native revisions against late rejected records rather than allowing them to overwrite the moved animal. ForceSendZDO queues publication; it is never treated as an acknowledgement.

During destination-owner phase three, allow at most three targeted snapshot refreshes and native RequestZDO prompts, spaced at least two seconds apart. Do not extend the ten-second phase timeout or the overall journey limit. Completion still requires an accepted newer owner-authenticated animal record at the destination; a ping or a resent snapshot alone cannot confirm it. Failed moved-animal handoffs release unconfirmed destination ownership to native assignment, retaining the animal's identity and relocated state. Successful handoffs retain their confirmed owner. Debug reservation endings include destination_retries; cancellation evidence uses the applicable pre-move or recovery distance. Escape-route wait reasons distinguish blocked corridors from a deferred search budget. These details use the bounded traversal and independent transaction-ending streams; normal grouped outcomes and immediate failures retain their existing boundaries.

Failure before movement cancels relocation. Interruption afterward leaves the single original animal at its recorded destination and reports separately whether ownership was confirmed. It does not recreate the source or retry a consumed traversal. Placement times out after thirty seconds; each ownership/confirmation phase times out after ten seconds. Cleanup relinquishes server ownership and releases unconfirmed destination ownership for native assignment; confirmed destination owners remain.

## Logging and acceptance criteria

Selection diagnostics share a further eight-record-per-minute allowance: scope counts and at most three nearest supported-animal samples per request, including rejected candidates. Samples identify player/peer, animal/prefab, eligibility reason, distance/range, saved-health presence/value, tame state, saved following and owner. Expensive candidate ordering runs only under the effective Debug policy. These samples cannot consume the command receipt/rejection allowance.

Only recognized command emotes are logged as command applications; emote-end counters still advance replay protection without command output, and first fresh player data has a separate state-observation message. Stay scope counts only associated candidates; nearby non-associated animals are labeled not following you or following another player. Pending stops and reclaims are labeled queued, separately from rejections. These records share the existing Debug allowance; recognized requests and concrete selection/actor/rate-limit rejection reasons are Debug command evidence, bounded to thirty-two records per minute. A stay request immediately replaces follow authority with a pending stop. Private pending feedback is followed by confirmed-stay output only after the idempotent stop handshake; a timeout warns without claiming confirmation. Actor-gate changes use a bounded sixty-four-player reason cache. No saved emote or follow name alone authorizes travel.

Reserve six Debug records per minute for substantive traversal entry/arrival/readiness, pair and follower gate reasons, consent loss and cancellations, six separately reserved placement-wait records, two separately reserved routine source-poll records, plus eight independently reserved transaction endings so repeated placement waits cannot consume final-outcome evidence. Movement/scope samples have a separate two-record allowance so repeated stop/resume changes cannot exhaust traversal evidence. Together with eight selection records and one controller plus one movement timing report, recurring output is bounded to sixty records per minute. Unchanged gate reasons deduplicate by player/stage/reason/portal/animal for five minutes in a 256-entry cache; semantic transitions retain each occurrence within the stream cap. Omitted traversal samples are counted in the next permitted evidence record. Ordinary outside-trigger/no-portal/awaiting-position/cooldown observations additionally allow at most one source-poll sample per physical peer per minute, using a bounded sixty-four-peer cache; they cannot consume substantive traversal slots. Pair evidence distinguishes source_unlinked, destination_record_missing, destination prefab/creator/position/scale/definition exclusions, destination_link_not_reciprocal, portal_tag_mismatch, portal_separation_invalid and portals_disabled. Pair samples include native source/destination IDs, target IDs, raw tags, source scale, destination creator and observed separation. Retained-witness expiry and changed-source/link/endpoint evidence are separate reasons. Fields include player/peer, source/animal IDs, observed positions, sample age/gap, range limits, consent order/age, and the expected exit as appropriate. Destination distance, overall traversal timeout, missing owner samples, out-of-range animals, altered following and wait-area movement have separate reasons. Placement waits distinguish terrain, prefab, retained-context capacity, collision instances and absence of a safe ground position. Under effective Debug collection, per-reservation totals record search attempts/candidates, rejection counts, context milliseconds and search milliseconds; timings include synchronous work only. Rejection counts distinguish insufficient portal-front clearance, missing terrain, water, vertical/radial range, slope, lava, uneven footprint support, player/creature/follower clearance, solid overlap, swept walkout collision, support-probe overflow, missing/blocked access paths, endpoint snapping, excessive route detours and physical wall collisions. Counts include landing and walkout probes, rather than unique landing positions. Final reservation evidence includes these totals, the last landing probe and its support height when accepted, follow_continues, the actual moved position and its signed forward/side offsets in metres from the destination portal (positive side is right); repeated waits retain the existing semantic deduplication and stream limits. Cancellation propagates its original reason to every affected animal reservation.

Normal output includes one named notice when a detected journey ends before any relocation, and the traveler receives a private HUD explanation distinguishing retained follow permission from consumed optional waits. A consumed waiting association cannot be rebuilt from its now-empty native following field by wait alone. Source detection gives private destination-wait guidance; completion confirms arrival or distinguishes recorded relocation from unconfirmed destination ownership. These are per-attempt outcomes, not periodic polling notices.

Normal output includes lifecycle/failures, one named result per confirmed animal follow/stay change and one named moved-count result per completed journey. Relocated animals without destination-owner confirmation are distinguished. Empty/unchanged passes are silent. Different player/journey results retain their identities. Optional Debug entry/transaction evidence uses the separate six-record substantive traversal, two-record routine source and eight-record ending budgets; scope samples retain their two-record allowance; optional formatting follows effective shared suppression.

Optional bounded cancellation samples identify changed portal/actor evidence, arrival timeout, movement outside matched endpoints and destination-clearance/traversal timeout. Transfer completion samples include original animal ID, phase, source-state barrier result, previous/current owner and native revisions, separating relocation from confirmed destination ownership. Placement caches static collider requirements and collects creature obstacles once per search; the bounded placement probes reuse that snapshot.

Optional follow-movement timing aggregates the changed BaseAI.Follow path, including its synchronous native MoveTo call, once per minute under effective debug. It excludes other AI/physics and deferred native work.

Optional controller-pass timing reports duration_avg_ms and duration_max_ms at most once per minute for nonempty scope. Collection follows effective debug policy and includes synchronous controller processing only; see [shared measurement limitations](../limitations.md).

Reservation-end diagnostics capture a controller-owned snapshot before cleanup, then format that snapshot after release. Include exact validation/cancellation reason, record identity, owner/revisions, position, saved following, health, tame/rider state, phase age and ordering-echo result. Owner-after-release is not used as failure evidence. Missing/replaced records remain unknown. Placement evidence counts one final rejection reason per candidate, so the counts sum to rejected candidates; walk-out step rejections and per-pass wait reasons are counted separately. A placed animal also reports the traveller's position when the landing was accepted and the landing's forward/right offsets and horizontal distance from it, in the portal-facing frame. Up to sixteen named entries each record which pieces caused `unsupported_surface` (prefab and reason) and which layer and object an overlapping body touched, preferring a placed object over terrain.
