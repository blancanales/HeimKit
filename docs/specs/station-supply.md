# StationSupply specification

Core cooperative admission pauses new discovery and transaction starts during native raids or detected combat. In-flight source draining, atomic commit/rollback, ordered client refresh, manual access and safe authority release retain their normal paths. Quiet resumption uses ordinary scheduling without replaying missed intervals.

## Behavior and server-only feasibility

StationSupply moves real items from one nearby player-built public stationary chest into each supported production intake. It does not collect outputs, tap fermenters, change production speed/capacity, keep distant areas loaded or feed during native sleep/time skipping. Clients remain unmodified. Follow [architecture](../architecture.md), [supported environment](../server-setup.md#supported-environment) and the [guide](../features/station-supply.md).

The installed native Smelter defines separate m_addOreSwitch and m_addWoodSwitch transforms, native conversion lists, fuel capacity and queue capacity. ShieldGenerator defines m_addFuelSwitch and its fuel list. The audited Frigid Kiln and spinning wheel prefab IDs are piece_FrostKiln and piece_spinningwheel. Fermenter defines an add switch (or its ordinary interaction body), native conversions, cover requirements and content. Their existing replicated ZDO fields can represent additions without changing client component settings. [AutoProcess](https://thunderstore.io/c/valheim/p/ArgusMagnus/ServersideQoL_AutoProcess/) provides a server-only feeding precedent; StationSupply independently uses the installed native contracts and intake-specific single-chest selection. Frigid Kiln ice occupies the native fuel slot and is treated as a processing resource, not assumed to be coal. Only audited vanilla prefab families and current native component contracts qualify; unknown definitions remain untouched.

## Intake selection and placement

Measure horizontal distance from the actual add-resource switch projected onto the station floor, not from the station centre or output. Each intake chooses the nearest supported chest pivot within ChestRangeMeters, with chest pivot height within ChestHeightToleranceMeters of the station base. Deterministic native-ID ordering breaks exact distance ties. For off-centre intakes, require the chest on that intake's outward-facing half-plane; centre intakes allow all sides. This keeps opposite-side storage separate while permitting floor-level chests below high hatches. Rotate anchors with the placed station. Recommend placing a chest just outside its hatch, leaving room for native use and output collection.

Selection ignores contents, open state and ownership. An empty, busy or unavailable selected chest makes that intake wait; never search another chest for the desired item. Re-evaluate spatial assignment when placement changes. One chest may serve multiple intakes if it independently qualifies for each, but no intake combines chests. Move up to `MaxItemsPerVisit` real compatible items per intake per completed visit, limited by native room and committed atomically; native conversion preference and selection order remain. Fermenters accept exactly one input. Fuel uses the native `fuel <= capacity - 1` check before each whole-unit addition; material inputs keep their own consecutive queue keys and item names. Public stationary chests require a nonzero creator. Private chests, cargo, carts, ships, tombstones, wardrobes, nonunit-scaled sources/stations and world loot are excluded. Respect enabled native ward access using the station creator as the automation identity; unavailable or unsupported protection data defers feeding.

Rotate the first intake independently for each placed multi-intake station on every eligible visit, including visits whose transaction later cancels. Other stations and single-intake consumers cannot advance its order. Keep at most 1,024 recently used multi-intake station identities through Core's access-order utility; discard the least recently used entry under pressure. Reset ordering on original-record replacement, prefab/intake-count changes or controller disposal. This retains at most `MaxActiveTransactions` active transactions over disjoint station and chest records and the existing candidate budget without repeatedly favoring fuel over material.

## Ownership and persistence

Consume Core world discovery, prefab metadata, typed native access and ordered ownership transfers. Never use a client-owned inventory snapshot directly. Drain each chest and station's previous connected owner through native state return and authenticated ordering echoes before mutation, fencing stale packets while retained. Station leases pause native production updates during the short drain/transaction so an old owner cannot spend fuel or process queues concurrently. Reject open/in-use chests before and after drain, retain originals only, revalidate identities/positions/selection/capacity and do not mutate player inventories. Unknown source ownership or timeout defer the operation. Raw native records suffice for ordinary stations; optional fermenters additionally require prepared surrounding roof/cover context and a live native instance. Release every lease on pause, cancellation, failure and shutdown.

A transfer parses the source inventory once, stages up to `MaxItemsPerVisit` units from compatible stacks in the same order as repeated single withdrawals while preserving other serialized item fields, and writes source inventory plus native destination fields synchronously in one atomic main-thread commit. No delayed add RPC or retry can spend the same item twice. Validate every selected item name and original stack before mutation; any invalid item cancels the whole batch. Compare source inventory and station capacity once immediately before writing. Roll back the source and every written destination field on synchronous failure, including every queue key's previous string, queued count, cheated provenance, fuel, content and start time. A batch retains cheated provenance if any moved item is cheated, preserving the existing already-nonempty-queue rule. Native world persistence stores both records; there is no second inventory store. Reload an existing server container's native inventory after commit and before it can regain ownership. Publish ordered same-ID closed-chest and ordinary station cache refreshes to ready clients before releasing leases. Fermenter station instances receive ordinary native state snapshots instead: their unreplicated DelayedTap callback must survive so previously tapped mead still spawns normally. Cache refresh waits expire after ten seconds without reversing an already committed transfer. Preserve native queued cheat provenance. Shared client/persistence limitations belong in [limitations](../limitations.md#stationsupply).

## Manual container access

Player access takes precedence over feeding. Source chests and the optional Obliterator destination opt into Core's deferred native container interactions. While such a record is leased, preserve the first authenticated native RPC_RequestOpen/RPC_RequestStack/RPC_RequestTakeAll with its original sender, message ID and eight-byte player-ID parameters. Require a current ready physical connection and an original, valid, peer-owned character within ten metres of the container; never turn arbitrary routed messages or remote/unknown actors into priority signals. Keep at most one deferred request per original object and sixty-four per authority. Mark the lease as manually requested rather than delivering an interaction into a fenced inventory.

Before commit, finish both source drains and then cancel the supply transaction without consuming an item if either container was requested. After commit, finish the existing ordered client refresh; never undo a committed transfer or expose stale inventory merely to grant access sooner. Release ownership normally. Only mark requests safe for replay when source state is confirmed for both records or a committed transfer's refresh acknowledgements completed. Unsafe cancellation, replacement, disconnect, world change and expiry discard the request; send the native negative response when the original connection/world is still usable. Do not fabricate a successful open response.

Core services safe deferred requests on a bounded cadence, waits for a current native owner, sends an ordered snapshot/barrier to a remote owner, rechecks ownership/record/connection/proximity, and routes the original request to that owner once. The normal container handler still checks access and busy state. A local owner also requires a live original view. Skip a deferred open if that same requester already owns an in-use container; stack/take-all operations still require their native handler. Do not change player ownership or inventory, bypass another consumer's fence, or invent a container owner. Retain requests for at most fifteen seconds, including the transaction wait; remove them before dispatch to prevent reentrant duplicates. Disposal discards deferred state and removes its schedules/barriers.

Observe supported container interactions through the existing routed-message subscription as well, so a request arriving outside a lease also prevents a new acquisition. Defer that original container for ten seconds after observed manual requests, observed open state or deferred-request completion; retain at most 256 recent objects, with a conservative global grace on overflow/clock rollback. Keep nearest-source assignment and never fall back during this grace. The same rules apply to loading/emptying an enabled Obliterator. Track manual requests, yielded transactions, replays and expired/unsafe/unavailable requests in the existing activity counts independently of Debug admission. Verbose activity reports include manual_queued, manual_yielded, manual_replayed and manual_unavailable; blocked-check reasons retain manual grace and individual unsuccessful replay reasons. Manual signals do not authorize extra world discovery or inventory parsing. Preserve ordinary interaction/privacy checks. Manual-access state and deferred work follow the existing player-presence/controller lifecycle.

## Obliterator intake

Obliterators=false disables disposal feeding by default. ObliteratorCategories defaults All. Once feeding is enabled, the selected supply chest supplies items in the selected categories; no individual item names are needed. Categories are Materials, Trophies, FoodAndMead, Weapons, Armor (including shields), Tools (including torches), Ammo and Other (including utility/trinket/miscellaneous items). None selects nothing. Classification follows native ItemType and skills. Consumable and Fish belong to FoodAndMead, along with material inputs whose audited native cooking/fermenter conversion produces a consumable. Derive those memberships from prefab conversions through the shared registry, not individual item names. Pickaxe skill belongs to Tools; axes match both Weapons and Tools. Unknown native enum types fall under Other when the registered ItemDrop definition remains valid. Filtering skips unselected entries within the same selected chest without selecting another chest. Resolve each selected registered native ItemDrop definition through PrefabRegistry before moving it. The feature uses one nearest public chest by the existing placement rules, at the native incinerator container's loading opening projected to the floor. Recommend the side opposite the lever. It never searches a second chest, pulls the lever, sends an incinerate request, changes conversion rules or removes output.

The audited incinerator has a child public Container referencing the persistent root ZNetView, with a native seven-by-three inventory. It uses a local delayed incineration coroutine and a nonreplicated busy flag. Both source and destination inventories must be closed before and after source-state drain. Stage up to `MaxItemsPerVisit` withdrawals and parse the native destination inventory once before mutation. Insert in withdrawal order and stop at the first item that cannot fit, retaining later items in the source; serialize each resulting inventory once. Merge only byte-equivalent item metadata apart from grid coordinates and stack encoding, within the native stack limit; otherwise use a free slot. Preserve all other item bytes. A full/incompatible destination consumes nothing. Commit both inventory payloads together with synchronous rollback and reload any existing native source/destination Container instances before publication. Reuse the original records and shared ownership/cache refresh service.

Observe authenticated native lever request/animation/return messages through the existing shared routed subscription. These callbacks record evidence only. Defer feeding for at least ten seconds after controller startup or a relevant lever message, with the interval enlarged to cover native effect delay plus its four-second busy cooldown. Track at most 256 recent object signals; overflow applies the same conservative quiet period to all Obliterators. Also reject a locally busy Incinerator instance. No gameplay runs independently of the existing presence/readiness lifecycle. The feature never invokes Incinerator.Incinerate or its lever handlers. Delayed/lost observations remain subject to [limitations](../limitations.md#stationsupply).

## Settings and bounds

Enabled=true; DebugMode=false. ChestRangeMeters=2 (0.5..4); ChestHeightToleranceMeters=1.5 (0.25..3); ScanRangeMeters=64 (16..128); IntervalSeconds=2 (0.5..10); MaxStationsPerPass=4 (1..16); MaxItemsPerVisit=10 (1..64); MaxActiveTransactions=2 (1..4). Set both new bounds to 1 for the previous single-item, single-transaction behavior. Obliterators=false and ObliteratorCategories=All control optional disposal input. Individual switches enable smelters, charcoal kilns, blast furnaces, windmills, spinning wheels, eitr refineries, frigid kilns and shield generators; fermenter filling defaults off. Configuration is bound through the shared loader and requires restart. All numeric settings must be finite. Native capacity, conversions, fuel costs, roof/wind/smoke and output behavior remain unchanged.

Bound work to a rotating player scope, at most 8192 discovered candidates and at most `MaxActiveTransactions` active transactions over disjoint station and chest records. Drain/instance waits expire after ten seconds. Idle passes do not deserialize chest inventories. Never scan the entire persistent world, create a second presence census or keep feature-local prefab metadata caches.

## Performance

Before acquiring either original, preflight both data revisions and native source connections. Revision zero cannot start a station handoff. Core NativeConnection reads the physical socket and, for PlayFab, requires the native CONNECTED state with PartyResetInProgress false; IsReady and IsConnected alone do not establish send readiness. An unavailable original connection cancels an uncommitted transaction without further state requests. Core retains up to 256 unresolved static source obligations, reserving capacity for active leases, so failed-drain release cannot convert an owner-zero snapshot into trusted inventory. Failed undrained static leases restore the previous network owner on release. A retry drains the same physical source; a replacement connection cannot inherit its acknowledgements. Record replacement discards the obligation; after the original connection leaves, a new native owner can become the new drain source. Invalid/removed obligations are pruned on a bounded five-second cadence. Capacity defers new acquisition instead of evicting unresolved source safety state. Disposal releases leases and clears consumer state.

Retain up to 256 failure delays by station/intake/chest, using Core access-order eviction. Unchanged ownership/drain failures retry after four seconds, doubling to a thirty-second ceiling. Record/revision/owner changes, original connection replacement and source transport readiness changes invalidate the delay on the next ordinary discovery visit. Our own acquire/release revisions do not reset escalation. Keep the ten-second active deadlines and at most `MaxActiveTransactions` active transactions over disjoint station and chest records; never retry a committed item mutation. New discovery participates in Core's four-millisecond cooperative admission budget; drain progress, refresh acknowledgements, manual requests and cleanup remain outside that admission gate.

Publish each ready client's station/chest refresh as one native DestroyZDO package followed by the two ordered original-ID snapshots and one ordering barrier. Fermenters omit station destruction to preserve DelayedTap. Both records stay fenced until the pair is acknowledged or its existing deadline expires. Retain every ready physical client, including distant clients: native per-peer known-record entries can be removed by sector invalidation while a client still retains a cache, so absence there does not prove a safe omission. A reconnecting original client remains pending; dispatch its pair when native sending resumes. A departed physical connection cannot donate its acknowledgement to a replacement. Each atomic batch uses one refresh group per client, independently of its item count, and retains the two ordinary cache-reset operations per client.

Partition the current borrowed Core scope into reusable station, chest and ward selection buffers once per discovery or final transaction revalidation. These are transient selections from that scope, not another world scanner or spatial index. Only station candidates consume MaxStationsPerPass, including ineligible stations; retain a rotating cursor so exclusions cannot cause an unbounded station sweep. Evaluate chest eligibility lazily, at most once per prepared scope and only when an intake needs selection; full stations and scopes without eligible stations must not trigger chest health/scale preparation. Project/normalize each intake once before comparing chest positions. Ward checks visit the current ward selection only. Keep all nearest-source, tie-breaking and exclusion rules unchanged.

Advance every active transaction sequentially on the same 0.2-second set cadence, refreshing its own anchored scope before use and rebuilding selection buffers before final revalidation. New transactions still require cooperative/combat admission and the rotating MaxStationsPerPass budget. Any station/chest overlap, including cross-role identity, blocks with `record_in_active_transaction`; nearest-source selection never falls back. Sleep skip, pause and disposal end every active transaction and attempt all releases before reporting a cleanup failure. Eight leases at the maximum concurrency remain within Core's 256 reserved source obligations and 64 deferred requests; their capacity guards and source obligations remain unchanged.

While ownership is draining, refresh current nearby-player eligibility through Core without reading world candidates. Refresh full candidates and protection/placement state once both drains are ready, before any inventory mutation. Native source-state retries, deadlines, ownership fences and client cache refresh ordering remain mandatory.

Discovery rotates only through reliable living outdoor actors, skipping dungeon occupants without spending an otherwise usable outdoor discovery visit. Keep all actor positions and movement segments in the shared clearance snapshot. In-flight RefreshAt validates the original station and the presence of any current living outdoor actor within range without choosing or advancing a discovery actor. An unrelated dungeon occupant cannot cancel that transfer. All actors unavailable, no outdoor discovery actor, loss of nearby outdoor presence, an interior station and oversized scopes still defer work. No additional roster census or world query is permitted during a drain-only check.

Retain at most 256 negative input decisions keyed by original chest identity and intake definition. Remember only a valid parsed inventory with no compatible/allowed item, after leases have been released and only if the parsed source record, data revision and inventory reference remain unchanged. An unchanged original record/data revision can reuse that negative result without another ownership handoff or inventory parse; replacement, destruction or any data-revision change invalidates it. Never cache successful withdrawals, destination capacity, ward permission or native ownership readiness. Do not retain serialized inventory buffers in this history. A cached rejection still blocks fallback and preserves its inventory diagnostic evidence. Clear all selections/history on controller disposal.

Diagnostic semantic identities use typed native IDs and wait/rejection fields; do not concatenate object IDs or stage strings before deduplication and budget admission. Optional timing reuses Core diagnostics, remains disabled with debug suppression, measures only scheduled controller work and allocates no measurement/closure on idle ticks. Performance diagnostics do not authorize extra discovery or gameplay work.

## Player-service integration

Plugin injects its existing PlayerServices. The module owns one presence subscription and at most one controller per ready world, following the [required hookup](../architecture.md#required-feature-hookup). Tick requires enabled/compatible dedicated-server world services, reliable joined-player positions and no native sleep skip. Empty/unknown presence disposes all controller resources before acknowledging pause; occupied readiness recreates them. No AFK activity lease or independent offline responsibility exists. Ready is reported once independently of player presence. Construction binds settings only; runtime failure uses shared persistent module-failure protection.

## Logging

Use shared FeatureDiagnostics, DiagnosticLog, debug suppression and stream limits. Normal output reports lifecycle/failures and one nonempty confirmed item count per sixty-second activity window, with a pending count flushed on controller disposal. Count only committed real-item moves; no per-item Info write occurs. Runtime errors retain station/intake/chest identity, transaction stage and committed state when a transaction exists. A client-refresh timeout warning identifies the committed station/chest and pending acknowledgement count and peer. Counts describe source inventory decrease and destination state increase, not player-screen delivery.

Debug supply records identify the station, intake kind, selected chest and exact observed wait/cancellation reason. Record full/invalid capacity, open/empty/unavailable storage, ward denial, station exclusions, sleep skipping, unavailable player scope and recovery. A failed placement records the nearest rejected supported chest, horizontal intake distance, signed height difference and rejection reason; its rejection counts classify each observed chest by its first failed rule. If assignment changes during a transaction, identify the new selected candidate. Do not scan additional objects to explain unsupported storage.

Inventory evidence comes from the existing transfer parse, without an extra deserialization. Distinguish empty inventories, incompatible resources, no category-eligible registered item, unsupported formats, malformed payloads, full destinations, size limits and concurrent source/destination/capacity changes. Stack and rejection counts describe the parsed inventory before transfer, not item quantities. A rejected-prefab sample is the first rejected entry, not an inventory listing. Source-state waits retain separate station/chest reasons for lease, record, owner, peer, barrier and returned-state readiness. Timeout evidence retains the last observed stage. Optional fermenter context/instance/roof/exposure and Obliterator startup/lever/overflow/clock/busy/category waits have distinct reasons.

Normal Debug records contain at most eight fields with the most relevant measurements for that outcome. Verbose replaces that record with expanded evidence on the same topic: positions/projected intake, configured distance/height limits, eligible/rejected chest counts, accepted resources or selected categories, sampled rejected item definition availability, native capacity, current/previous owners and revisions, source observation state, transaction stage and pending refresh peer identities. Label selected measurements selected_distance_m/selected_height_m, and rejected evidence rejected_candidate/rejected_reason/rejected_distance_m/rejected_height_m. A rejected candidate never describes failure of a successful selected chest. selection_checked and selection_counts_measured distinguish actual selection/counting from unobserved state; omit chest-count fields unless counts were measured. Preserve meaningful zero/false values. Never dump inventory payloads, custom item metadata or routed packets. Optional collection failures must not interrupt transaction cleanup or gameplay.

Retain at most 256 station/intake/chest identities per controller. Suppress unchanged semantic reasons only within that identity; preserve changed placement rejection/candidate and ownership-wait stages while ignoring advancing times/revisions. Budget-denied observations remain eligible for later emission. Reserve the twelve detailed supply records per minute as six blocked-condition samples, four terminal transaction outcomes and two progress samples. Successful resource/refresh stages use aggregate Debug counters rather than detailed records; ordinary confirmed-transfer Info notices remain unchanged. Allow one scope summary and one nonempty activity summary per minute, and one settings declaration per controller, within the shared sixty-record ceiling. Scope summaries identify omitted attempts by stream. Terminal Debug evidence includes `batch_size` without per-item records. Transfers and the normal "Moved N real resources" notice count moved items; transaction starts count batches. Activity summaries retain transfers, transaction starts, cancelled uncommitted transactions, actionable failure occurrences, source-state request calls, client cache-reset calls, completed refresh groups and blocked-check counts since the previous activity report. Verbose also includes ordinary state-snapshot calls. These counts describe checks/operations, not unique problems, packet/byte counts or discarded resources. Maintain counts independently of Debug admission and reset only after an admitted activity report. Bound retained reason keys to 128; combine excess keys under other. Empty/unchanged passes otherwise remain quiet. Settings declarations name enabled native station families, optional modes, categories and placement limits. Clear diagnostic history with controller disposal.

Timeouts, malformed/unsupported inventories, invalid resource stacks, inventory size-limit failures and identical source/destination records are actionable incidents. Warn independently of optional Debug policy/budgets, identifying station/intake/chest, last observed stage/waits, committed state and pending refresh peer/count when applicable. Retain at most 256 current incident identities. Report first/changed failures immediately, combine unchanged repeats into a five-minute reminder with suppressed count, and report recovery once after a transfer and its refresh acknowledgements complete. Native placement, full/open/empty storage, incompatible resources and ordinary ownership readiness remain Debug conditions. Detailed terminal Debug evidence keeps its independent allowance even if blocked/progress samples are exhausted. Runtime exceptions keep the existing immediate Error/failure-protection path.

Core ProcessingTiming reports one overall timing record and at most one record per registered active stage per reporting window under the same effective debug policy and shared ceiling. Register world_discovery (including current actor eligibility), chest_selection, ownership, inventory_read, commit, client_refresh, native_context, diagnostics and diagnostic_fields. The latter measures admitted optional evidence/field preparation before formatting and logger dispatch. Shared ServerPerformance separately measures DiagnosticLog formatting and synchronous listener dispatch, independently of Debug. Report calls, average milliseconds and maximum milliseconds; flush stage aggregates with the overall pass window, subject to shared optional-output admission. Ownership includes acquiring, draining and releasing; client_refresh includes paired native cache/snapshot dispatch and acknowledgement checks. Preserve source-drain fences, original-ID replacement and snapshot-before-echo ordering. Operation counts distinguish reset/snapshot work without claiming network bytes. The overall scope is the prepared station/chest/ward count; measurements cover scheduled synchronous controller processing, not time awaiting peer acknowledgements. Retain the scope callback once and use value measurement scopes, so no timer object, delegate or scope snapshot is allocated on an idle tick. Throttle sleep-skip diagnostic checks to the configured discovery interval.

## Acceptance criteria

Fuel and material ports select independently from their true rotated anchors. Wrong-side/out-of-range/other-floor chests never supply a port. Empty or busy nearest chests prevent fallback. Each successful atomic visit moves up to `MaxItemsPerVisit` real compatible items within native room without modifying unrelated inventory bytes; every moved item is consumed exactly once, and any failure before commit consumes nothing. Fermenters remain limited to one item. At most `MaxActiveTransactions` transactions may run over disjoint station and chest records. Native ownership handoff, source-state return, pause/reconnect, world replacement and failures release only this consumer's leases. StationSupply remains independent of every other module, including InfiniteTorches and TameTravel.

## HeimKit Core integration

StationSupply consumes Core IncomingPackets through ObjectTransferAuthority and PlayerRoutedMessages for shared peer/header inspection and retained-ID filtering. Source-drain state, ownership fences, acknowledgements and manual-access policy remain unchanged. NativeInventory owns bounded batch parsing and byte-preserving inventory serialization; PlayerWorldScope owns discovery and anchored actor/selection refreshes.
