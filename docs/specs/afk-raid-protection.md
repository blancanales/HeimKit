# AfkRaidProtection specification

## Local automatic-raid protection

AfkRaidProtection defaults enabled and filters new automatic random-raid candidates only when at least one player is in the native event area and every nearby connected player is reliably observed as inferred idle. An active, sleeping, dead/loading or uncertain nearby player retains native raid eligibility. A known active player elsewhere does not change an AFK-only area's result. Unknown player position/data prevents suppression rather than assuming the player is elsewhere. Native horizontal event range and the native dungeon-height exclusion determine locality; no arbitrary global protection radius is substituted.

Existing events continue. Explicit admin random-event starts, named events, forced/scripted events and standalone event paths are unchanged. The supported game's RandEventSystem.UpdateRandomEvent owns automatic scheduling; StartRandomEvent/GetPossibleRandomEvents/GetValidEventPoints select targets. A scoped hook filters GetValidEventPoints only inside the automatic update and only for normal random events. It preserves native biome, base, progress/global-key, chance and timer conditions. No direct StartRandomEvent/SetRandomEvent cancellation or event reset is added.

## Configuration and lifecycle

`[AfkRaidProtection] Enabled = true` controls the feature independently of either sleep module. The [shared activity contract](../architecture.md#shared-player-activity) and [settings](../server-setup.md#player-activity-and-sleep) apply. Disabling this consumer removes only its raid hooks; shared tracking continues if sleep exclusion still requires it. When no AFK consumer is enabled, the shared activity observer and polling are removed. Tracking failures/unknown state retain native raid behavior.

Config definitions belong in AfkRaidProtectionSettings, lifecycle in AfkRaidProtection, filtering/counters in AfkRaidProtectionController and bounded formatting in AfkRaidProtectionDiagnostics. The [hidden debug suppression policy](../server-setup.md#hidden-per-feature-debug-suppression) does not disable required activity collection or gameplay filtering. Ordinary readiness/warnings/errors remain visible; summaries are limited to once per minute and candidate decision samples to six per minute; separate actor and native-outcome stream bounds are defined below.

## Evidence and limitations

Primary evidence is the installed supported assembly: RandEventSystem.UpdateRandomEvent, GetValidEventPoints, StartRandomEvent, ConsoleStartRandomEvent and SetRandomEventByName; ZNet ready-peer/character association; replicated player fields and routed RPC headers. See [supported environment](../server-setup.md#supported-environment). Existing native event selection uses peer reference positions, while activity observes associated character data; absence of a reliable nearby observation never proves an AFK-only area.

[AFKManager](https://github.com/Torokal/AFKManager) is an MIT-licensed mechanism reference; its code is not copied. Our observed activity signals and limits are specified separately. Idle inference cannot see every local inventory/menu action. The feature prevents eligible new random raids at inferred-idle-only locations; it does not grant invulnerability, prevent other enemies, stop running raids or establish universal compatibility with event mods. Vanilla clients require no custom handlers or installation.

## Diagnostic evidence

Ordinary registration records name the automatic update, candidate selection, possible-event result, native start request, keys/biome/base gates and native event setter hooks. Invocation counters distinguish registration from execution. Empty native candidate results, empty possible-event results after filtering, native candidate records/valid points/rejections, gate pass/rejection totals, scope exclusions, not-ready fallback and native exceptions are distinct. Record totals are per event-selection invocation, not distinct players or locations. Key/biome/base gate counts observe native returns inside automatic updates, including standalone iteration; short-circuit conditions that were never called are not invented. A pre-selection key rejection can explain why no candidate hook ran, but not a complete unavailable per-player rejection history.

Optional schedule probes sample the native event timer, interval, event-rate and chance settings at most once per second and report probe age. A sampled threshold is not an observed chance-roll result. Automatic and explicit/other start-request counters distinguish those paths. Candidate samples describe locations already emitted by the native selector before AFK filtering. They report native range and known nearby idle, active, bed and dead/loading populations, plus unknown, dungeon and outside actors. A known active distant actor remains outside that location; an unknown actor prevents suppression. Native geometry/key checks are not rerun to manufacture a reason.

Read-only SetRandomEvent observations distinguish a completed setter producing a new matching server event from unchanged state, clears, a different result or native exceptions. StartRandomEvent return observations independently show whether its server event state changed; they do not double-count setter-observed starts. Automatic random, automatic standalone and explicit/other origins are labeled. The latter does not guess whether the caller was an administrator, script or another mod. Observed server event state does not establish spawned enemies, client receipt or which feature caused it; causality is unknown. Already running/forced/admin events retain native gameplay.

The one SUMMARY per minute includes invocation/rejection/empty/outcome counters, latest outcome and age, omitted samples and unchanged-candidate counts. Candidate status changes take precedence over repeating identical location/reason records; its comparison cache holds at most 256 entries. There are separate allowances of six candidate RESULT records, six native-outcome RESULT records and six prioritized AFK actor DETAIL records per minute. AFK state sampling uses the bounded optional transition contract in [AfkSleepExclusion](afk-sleep-exclusion.md#diagnostic-evidence). These are bounded independent streams, not promises of a record for every event. Native exceptions and observation failures remain separate; an optional probe failure warns without disabling or rewriting gameplay. Effective debug suppression skips population probes, native state snapshots and actor history. Readiness/warnings/errors remain visible and cheap counters continue.

Diagnostic observers have separate Harmony identities from gameplay controls. A failed observer registration reports its named hook with registered=false and retains gameplay hooks. Readiness lists only successful registrations. Initialized counters expose measured zero calls/results; an unavailable observer is identified by its registration warning rather than treated as working.
