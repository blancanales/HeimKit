# Server upgrade compatibility

## Policy

`Configuration/GameVersionCompatibility` owns the audited game baseline listed in [supported environment](../server-setup.md#supported-environment). The generated `[Compatibility] AllowUnverifiedVersions` switch defaults to `true`. It permits a reported game version that differs from the audited baseline, including an older version. `false` permits only the audited baseline. Missing, blank, control-character-containing or overlong observed version identifiers are rejected in either mode. A future version naming format does not itself prevent permissive operation. An invalid or unreadable configured switch uses strict mode and warns once.

The retired `SupportedValheimVersion` key is consumed and removed on configuration save. It cannot select an additional version or override the new switch. Existing values for the new switch and unrelated settings are preserved. The policy is immutable for a configuration session; restart applies edits.

## Startup backup gate

A permitted Valheim version newer than the audited baseline requires one verified world checkpoint per world/save location and HeimKit/Valheim version pair. The tested baseline is unchanged by allowing a version or recording a backup. Each startup checks the persistent record; a matching verified checkpoint is reused without copying the world again. Equal or older numeric versions and strict-mode version rejections do not request this backup. Numeric components are compared with absent revision components treated as zero; prerelease suffixes do not change numeric ordering. If a future naming format cannot be ordered, the same one-time checkpoint is required conservatively and the uncertainty is logged. This is a shared startup/save-management responsibility, independent of player presence and feature Enabled settings.

Core installs a guarded prefix on the dedicated server's native world-loading entry point. It identifies the selected local world through native save-path APIs and copies its complete active save format: the entire chunked-world directory or both legacy database/metadata files. Missing required world data, unsupported storage or unavailable native startup/save APIs blocks HeimKit activation. Vanilla world loading continues. Backup success is required before player/world processing and module initialization can begin; a pending or failed backup cannot be treated as readiness.

`Core/World/WorldUpgradeBackup` owns the durable record in `HeimKit/Backups`. Its key combines world UID, canonical save directory, full HeimKit build identity and observed Valheim version. The XML records who initiated the backup, capture ID, UTC start time, tested baseline, archive filename, byte length, SHA-256 and completion state. A process/startup identifier is not part of the key.

The attempt and expected archive filename are written atomically before copying. After archive/source verification, the archive digest is durably recorded before its final rename; only then is the record marked complete. An interrupted final rename or completion-record update can recover that same verified archive without another world copy. Concurrent requests for one key are excluded with a file lock. A matching completed record is reused only after its archive identity and checksum are verified. The current live world's later content is not compared with the old checkpoint. Missing or invalid records/archives require a replacement of the current world with an explicit explanation; access/record-write failures stop activation rather than cause duplicate copies. Completed archives are not overwritten or automatically removed.

The ZIP also contains the existing SharedMap and ForestRenewal directories and the active `heimkit.cfg`, with archive paths that keep each source distinct. Backups reside in `HeimKit/Backups` under the active loader configuration directory, outside the copied state directories. A unique UTC timestamp and identifier prevent replacement of an earlier backup. There is no automatic deletion or restoration.

Capture is bounded to 100,000 filesystem entries. Source enumeration rejects reparse points, duplicate archive entries and overlapping backup/source locations. Source files are held open against writes and deletion during capture. The source inventory is checked again before completion. The archive is reread and compared with the source contents before a temporary archive is renamed to its final ZIP name. Failure leaves no completed backup and keeps all HeimKit modules inactive for that startup. Large worlds can delay startup; operational and recovery details belong in [world backups](../world-backups.md).

## Feature isolation

Allowing an unverified version changes the version policy only. Feature construction, native member resolution, patch-shape checks, readiness, controller creation and runtime processing retain isolated failure handling. A failed module shuts down its hooks, subscriptions and retained ownership; unrelated healthy modules continue. A shared configuration or mandatory backup failure prevents all module activation.

## Persistent feature failure protection

Core records exceptions that actually disable a module, including construction/startup failures, controller and native-callback failure handlers, and later runtime failures. Warnings, normal readiness waits, configuration-disabled modules and recoverable diagnostic errors do not identify an unstable module. ModuleHost and each module's explicit failure path report through the same Plugin-owned service; text logs are not parsed to infer failure.

The durable `upgrade-<identity>.failures.xml` file sits beside the matching world-backup record. It identifies the world/save location, full HeimKit build and Valheim version, and links each first disabling failure to the available world-backup record/archive. It retains the module name, UTC failure time, operation and bounded exception evidence. This file is independent of the backup-completion XML, so record recovery or replacement of a missing archive cannot erase disabled-module decisions. On audited versions there may be no automatic world-upgrade archive; the failure record explicitly reflects that absence instead of claiming a backup exists.

Failure protection is loaded before module initialization. A recorded module is not initialized or ticked on subsequent startups for the same identity, even when its configuration requests Enabled=true. Module initialization guards and live enablement paths enforce the same effective override; configuration values remain unchanged. Construction failures occurring before the world is selected are queued and committed when that identity becomes available. Other modules continue independently.

A different world/save location or HeimKit/Valheim version pair uses a different file and performs its own checks, without deleting the previous failure history. A deliberate operator reset while the server is stopped can remove a selected disabled-module entry; ordinary restarts and Enabled edits do not reset it. Failure records use atomic writes and bounded parsing. An unreadable/malformed protection file blocks module activation. If recording a new failure fails, that module remains blocked in memory, an immediate error identifies the persistence failure, and shared processing stops rather than continuing with unreliable protection state.

This file records observed failures for a version combination; it does not prove that the game update caused them or that every successful startup exercised every gameplay path. Operational reset and observation qualifications belong in [server setup](../server-setup.md#persistent-feature-disables) and [limitations](../limitations.md).

Plugin owns orchestration. Configuration owns policy and migration. Core owns startup interception and filesystem backup; feature folders do not own another backup service or compatibility loader. No gameplay feature or player-presence lease is created for backup processing. The [architecture](../architecture.md#configuration) and [Core ownership table](../architecture.md#core-layer-and-anti-duplication) govern placement.

## Logging

One Warning identifies permitted operation on an unverified version and the audited baseline. Startup output states why the recorded world backup is being checked. Creation and reuse name the world, HeimKit version, Valheim version, original UTC capture time, archive and record paths. A reused checkpoint explicitly states that no new world copy was made; interrupted-record recovery is distinguished from a new capture. An invalid or missing prior checkpoint produces a replacement warning. A backup/native-hook failure emits an immediate Error with exception evidence and states that HeimKit remains inactive while vanilla loading continues. Individual feature failures retain their feature identity and lifecycle error. The first disabling exception per module/version identity writes its durable record and logs the record/backup paths; repeated reports preserve that first evidence instead of rewriting it. Each startup reports the loaded protection identity, count and paths, and one Warning per recorded module explains the enable override, first failure UTC/operation and compatible-release recommendation. These persistence and override notices belong in normal output even when DebugMode is off. Optional controller samples and repeated diagnostic evidence remain in Debug under the existing shared policy; text log sampling never determines a persistent disable. Repeated compatibility checks do not repeat the shared warning.

User-facing observation, migration and recovery caveats belong in [limitations](../limitations.md), not in claims of guaranteed compatibility.
