# SharedMap specification

## Scope

SharedMap owns persistent community exploration, vanilla cartography-table map fields, and independently configured portal, resource, dungeon, runestone, recurring-spawner and structure markers. It runs on Windows dedicated servers and in private or Start Server worlds hosted by the Windows client. Guests can use the vanilla client. Follow [architecture](../architecture.md), [contributing](../contributing.md), [supported environment](../server-setup.md#supported-environment) and the [user guide](../features/shared-map.md). Gameplay/client limitations are maintained once in [safety and limitations](../limitations.md#sharedmap).

The F7 switches for `PortalMarkerSync`, `ResourceDiscoverPreviouslyExplored`, `ResourceRemoveDepleted`, `DungeonDiscoverPreviouslyExplored`, `AllowPlayerMapWrites` and `SharePinCheckmarks` apply in place after the existing idle boundary. SharedMap invalidates cached table reconciliations and retains its loaded world stores. Enabling portal markers refreshes the native portal list immediately.

### Player-hosted worlds

The host’s native minimap exploration pass reveals the same bounded circle in the world’s community mask. The host participates in marker and nearby table sampling through Core’s local actor identity. Remote guests continue to contribute through accepted replicated character samples. The host’s native routed pickaxe damage and digging calls provide local Silver discovery evidence under the same tool, actor and range checks. A bounded queue defers nearby discovery work to the resource pass.

The outer host Read Map and Write Map actions reconcile the current table once. The inner read used by native Write Map consumes that result. Native AddSharedMapData imports community pixels and shared pins while retaining the personal map. The native MapData handler applies uploads on the table owner. HeimKit uses the shared map-field normalization on the host’s ZDO writes and on accepted guest replication, with unchanged inputs eligible for reconciliation cache reuse. Denied uploads and malformed bytes retain the accepted field. Native map callbacks leave persistence to the module lifecycle.

Local stores live under the active world’s `BepInEx/config/HeimKit/Worlds/<world-id>/SharedMap` directory. Both local hosting modes use the same UID whether Valheim’s save is cloud or local. World changes and disablement dispose native hooks, capture queues and reconciliation state and flush accepted community data.

Periodic table validation checks the complete contiguous terrain mask directly, retaining strict boolean, size, pin-format and trailing-byte rejection. Terrain/pin output equality uses span comparisons rather than per-byte enumerable iteration. Optional pin comparisons require shared Debug admission and are limited to six per minute; periodic server reconciliation supplies its already-validated original and normalized pin data, including removed death pins, without another decompression. Other native upload paths retain full validation; they never gate accepted-data validation or gameplay counters. Narrow elapsed stages and input-size/collection evidence use the shared normal performance path, independently of optional Debug.

Periodic table work uses one captured compressed source at a time and queues at most MaxTablesPerPass nearby table IDs per ordinary table cycle. Shared Core WorkSlice bounds each admitted main-thread update to a soft two milliseconds and sixty-four units. Decompression, boolean validation, terrain union/copy/import and compression yield every 32 KiB; pin validation/publication/encoding yields every sixteen records. The decoder rents one bounded scratch buffer and returns it on completion, error or cancellation; output arrays remain immutable. There are no worker-thread Unity or world accesses. Final table writes occur only after the pipeline completes and the captured map field still matches. Changed source fields, external pin-state transitions, removals or publication revisions cancel stale work; later ordinary cycles revisit the table. Community exploration remains a monotonic union, and changed marker/terrain inputs invalidate the reconciliation cache for the following pass. Native incoming and explicit administrative writes retain synchronous complete validation and normalization.

Normal performance evidence measures only active slice time, never suspended wall time. Its table_decode_slice, table_validate_slice, table_merge_slice, table_pins_slice, table_compression_slice and table_import_slice stages identify remaining expensive units. Optional grouped scope Debug reports tables_queued; completed table changes and invalid-data evidence retain the existing result/failure grouping.

Runestone metadata uses Core PrefabAssetRequest to start/poll one native asynchronous reference, releasing it on completion, timeout, error or controller disposal. Core scene-scoped catalogs retain pure runestone, spawner and structure classification across player reconnects and clear it with scene identity. No synchronous location-asset wait is used. Metadata inspection elapsed work and bounded optional asset outcomes share the existing performance/Debug paths.

## Exploration and accepted table data

Use the loaded Minimap's grid size, pixel size, exploration radius and interval. Match native WorldToPixel rounding and the integer pixel circle with radius ceil(radius / pixel size). Reject invalid geometry rather than substituting defaults.

Sample the shared peer snapshot: ready joined characters, valid owner-matching character ZDOs, finite positive health, finite positions, and no dead/interior-height state. Public player-map visibility is irrelevant. Do not substitute connection reference points. Reveal endpoint circles without interpolating travel.

Union fully validated existing/accepted table exploration with the community mask. Preserve prior accepted terrain when a later upload contains less. The player-write policy selects the prior server field before normalization when uploads are disabled. Readers receive vanilla shared exploration; no per-player terrain attribution is created.

Periodic pin normalization encodes the small pin tail separately, then copies unchanged terrain once into an exactly sized output array. Validated source bytes remain immutable. Existing pin order, native format versions, checkmarks, authors, exclusions, death removal and exploration union remain mandatory.

## Community persistence

When the world has no community file, complete a first-run import before player capture/table hooks. Use native iterative prefab lookup to scan saved cartography ZDOs, including distant records. Deduplicate identities; process at most MaxTablesPerPass payloads per tick. Import valid terrain only, leave tables unchanged, and summarize invalid payloads once at completion. Save the complete union, including an empty checkpoint. Interrupted imports have no completion checkpoint and retry on startup. Existing damaged files or orphaned backups are storage failures.

Store `world-<world UID in hexadecimal>.map` under `HeimKit/SharedMap` in the loader-provided configuration directory. Validate schema, world UID, grid dimensions, pixel size, packed bitmap length and checksum. Incompatible or unreadable state disables SharedMap without replacement.

Dirty saves use SaveIntervalSeconds. Flush accepted state on empty/unavailable presence, world/geometry replacement, failure and shutdown. Write a unique temporary file beside the destination, flush it, then atomically replace while retaining `.bak`; unchanged state produces no write. Retain accepted state across ordinary pauses. Radius/interval changes may reuse pixels only when grid dimensions and pixel size still match. Backup/recovery procedures belong in [world backups](../world-backups.md#sharedmap-data).

## Automatic portals

PortalMarkerSync uses ZDOMan.GetPortalList at each TableIntervalSeconds pass. On normalization, resolve live identities and require a nonzero Piece creator, finite exterior coordinates and community-explored terrain. Read accepted ZDOVars.s_tag; blank tags become `NoName`. Both connected and unconnected endpoints qualify.

Use Icon4 and a reserved SharedMap owner with empty author. Unconnected singletons have a separate reserved owner for rendering and share the same stable source key as connected portals. While enabled, replace all table Icon4 pins from the authoritative catalog, regardless of prior owner/text. Remove stale managed names, positions, deleted endpoints and duplicates, including reuploads. For other icons, remove obsolete portal-label matches (case-insensitive) within three horizontal metres of a generated publication. Always preserve player-owned hammer pins. Other generated sources are replaced from their own catalogs. Disablement removes service-owned portal pins and preserves player-owned records.

Stable identity uses exact finite saved prefab/position, normalizing signed zero, instead of session ZDO IDs. Exclude ambiguous overlaps. Recover legacy native-ID publication state only when its actual position (published position minus slot offset) uniquely matches within half a metre. Unmatched/ambiguous histories start fresh.

PortalClusterDistanceMeters uses stable identity order. Assign each portal to the nearest existing first-portal anchor within the configured horizontal distance; use stable first-group tie handling. Anchors stay fixed and grouping is non-transitive. Singletons retain their tag. Groups publish `Multi Portals (N)` at the members' arithmetic XYZ centre. Zero disables grouping.

SharedMapMarkerRefresh keeps actual and published coordinates separate. New markers start at the actual point. Label changes select from nine slots: centre plus a two-metre grid, at most about 2.83 metres away, and more than 1.1 metres from the previous publication. Unchanged labels retain their slot. Stable portal/group-anchor identities own history. Persist labels, slots and last published positions in `.portal-pins`; prune no-longer-eligible identities and cap at 4096.

If obsolete-pin cleanup finds a record within the native matching range of the current publication, select and persist another slot more than 1.1 metres from it, then regenerate table data. Repeated stale uploads retain that correction. Portal objects and unrelated world fields never move.

### Portal connection highlighting

Apply the existing portal grouping distance to all eligible discovered portals before assigning connection status to a pin. A group of two or more always publishes one ordinary grey `Multi Portals (N)` pin. Its members count toward the group regardless of their tags or connections. An unconnected member at a base does not produce a separate pin or change the group's label or colour.

For a standalone portal, use the native portal connection ID that Valheim uses for its hover text. An empty destination ID highlights the portal whether its tag is a name or the blank-tag label `NoName`. A HeimKit client shows the unconnected pin in white and restores its ordinary shared grey when the portal connects. A vanilla client reading the host's table can identify a standalone unconnected portal by the status appended to its label. With grouping disabled, each eligible portal is standalone.

The host publishes grouping and connection status through the existing catalog. Use the host's group membership on connected clients, including when only one member of a known group is locally visible. On an unmodified host the client can use locally observed portal records. A distant endpoint being unloaded does not establish disconnection. Read Map supplies the host's latest community discoveries beyond automatic delivery range.

Retain the existing discovery, visibility and administration rules. Use the bounded registry and nearby discovery passes. Invalidate cached publications when the displayed status or group membership changes. Carry the status independently of the player's tag, and reuse stable source keys to reconcile updates and table reads without duplicate pins. Preserve shared-pin ownership and personal notes. Client observations affect only the personal map. Host debug records group size and status transitions by source key, and client debug records the corresponding pin update. Acceptance covers named and unnamed island portals, connecting and disconnecting a standalone portal, and an unnamed unconnected portal inside a base group producing only the ordinary group pin.

### Client refresh for known distant portals

With Automatic markers enabled, the client observes native portal records on vanilla and HeimKit hosts. It indexes known managed portal pins from local discovery and table imports by stable source key. Round-robin checks visit up to four known pins per quarter second, pausing two seconds between rounds. Each lookup borrows native portal sector lists within the combined publication offset, rejects ambiguous matches and skips sectors above 256 portal records. A missing record leaves the last observed status in place for the session. Nearby discovery also reads the separate portal sector lists in slices of 32 records.

The client uses the matching portal's native connection ID to display the unconnected suffix and white icon, or the connected label and shared grey icon. The correction affects presentation only. Read Map, Write Map, pin ownership, saved pin data and checkmarks retain their normal behavior. Group pins and personal notes are excluded. On a HeimKit host, existing category and grouping policy applies. On a vanilla host the client can update portals it has discovered and for which Valheim has supplied a record. No status request or table interaction is required. Client Debug records changes by stable marker key, native portal ID, status and position.

During the battle pause defer discovery and ordinary table processing; accept terminal evidence for a known identity with a direct lookup. Mark the catalog dirty and coalesce publication through ordinary SharedMap scheduling. Group discoveries and retirements in the existing resource summaries. Bounded Debug evidence identifies the pillar, position and transition reason, including dead-flag, destruction or authoritative missing identity after reload; use existing elapsed and item-count diagnostics. Acceptance requires independent nearby pillars, idempotent retirement across duplicate or reordered observations, restart-safe cleanup and preserved static Flametal and ordinary ocean Leviathan behavior. Personal-map delivery follows [client map updates](../limitations.md#client-map-updates).

Associate deposits with skulls using native placement evidence independently of the configurable marble clustering distance. Keep skull identity through fracture. Use a bounded spatial lookup and reject ambiguous matches. A positively observed unpaired tissue deposit gets its own `(ST)` dot. Grouped skulls with active tissue use the lowest active tissue discovery ID as a stable pin location. Preserve one dot per associated group even with clustering disabled. Use the existing presence-gated Core candidate feed, retrospective discovery budget, accepted native health and destruction observations, and cartography-table refresh. The host supplies labels through Read Map to vanilla and HeimKit players in private, Start Server and dedicated worlds. Use existing table permissions and packet bounds. Clients cannot declare deposits or their health. Keep grouped discovery and depletion in normal output. In Debug, include deposit and skull identities, association or skip reason, fracture handoff and refresh timing with candidate counts under existing volume limits.

Ordinary discovery uses the same usable-character sampling and horizontal exploration radius as terrain. ResourceDiscoverPreviouslyExplored additionally accepts eligible records whose source position is in community-explored terrain. This optional scan advances one native prefab step and at most 256 queued records per tick; completed passes repeat no faster than TableIntervalSeconds. Nearby sampling uses rotating per-player candidate budgets. Silver always retains the mining rule below.

Persist discoveries and mining-section evidence in `.resources`. Assign increasing discovery identities; native ZDO IDs are transient bindings. Reassociate by same family/saved position only when unique within half a metre. Ambiguous matches stay unknown. Intact-to-fractured replacements continue one discovery. Keep confirmed depleted records as anchors/tombstones. Retire only native terminal destruction or fully validated health showing every section depleted. Missing records/invalid health retain the last accepted state. ResourceRemoveDepleted selects active-only or historical publication.

Other resources retain their short label.

Use Icon3 and reserved owner long.MinValue + 1. Replace only service-owned resource records; preserve player dots regardless of label. Reuse publication slots in `.resource-pins` for label/count changes. Cap discoveries at 65536 and generated resource markers at 4096. Rebuild grouping/publication caches only after accepted/configuration changes. Read earlier store formats without inventing section/mining evidence and save extended formats after real changes.

### Ancient Root discovery and sap reserve

ResourceMarkerSync also records exact persistent outdoor YggdrasilRoot prefabs with a validated native ResourceRoot component and finite positive maximum reserve. Its existing Plugin-injected player-service lifecycle, position sampling, retrospective opt-in, bounded candidates, cooperative combat admission, publication and persistence are reused. A prefab or extractor alone is not discovery: a root must pass ordinary near-player discovery, or the configured community-exploration retrospective rule. No new scanner, ownership request, live scene creation, collector interaction or native drain/regeneration call is introduced.

Publish one `Ancient Root N%` dot per discovered root at its saved source position, independent of resource clustering. N is floor(100 times the last replicated native float level divided by the prefab's maximum); absent native level uses the same maximum default as ResourceRoot.GetLevel. Invalid/nonfinite/out-of-range values establish no percentage, displaying `?%` when none was accepted. Do not infer elapsed regeneration, extractor fill, extractor presence or extraction readiness. Valid newer levels update persisted sap percentage, including increases after regeneration. A temporarily empty root remains discovered and visible at 0%, even with ResourceRemoveDepleted enabled. Only accepted terminal root destruction retires it; historical display labels a retired root `Ancient Root (removed)`.

Append AncientRoot after existing persisted resource-kind values. Resource-store format 4 adds one signed percentage integer per record (-1 means unobserved); formats 1-3 retain their existing parsing and defaults. Without skull bounds or tissue discoveries, write format 4 for root discoveries and format 3 otherwise. Mining-section progress remains separate from root reserve. Missing/unloaded or malformed observations retain the last accepted value. Normal discovery/retirement results and bounded Debug publication/catalog evidence use existing grouping and ceilings. The common resource-marker proximity display rule and personal-pin preservation still apply; observation/client limitations belong in the limitations page.

### Silver discovery observations

Subscribe to Plugin-owned PlayerRoutedMessages without acquiring AFK tracking. Validate authenticated character owner, health, position, equipped-pickaxe metadata, target, impact and player distance. An air swing alone is insufficient. Terrain requests must identify the native pickaxe dig operation and terrain-compiler target. Direct damage requires Pickaxes skill, positive pickaxe damage and the authenticated character as attacker.

A direct eligible-vein hit selects that vein regardless of centre distance. Otherwise choose the nearest undiscovered/nondepleted eligible Silver within SilverDiscoveryRadiusMeters of a qualifying impact, breaking ties by native identity. Use source coordinates. Persist the unlocked flag across fractured successors; older Silver records lacking evidence remain hidden until a qualifying impact. Only unlocked veins enter groups.

For client-local digging, compare validated terrain-compiler baselines after accepted ZDO deserialization: operation count advances, height decreases and last-operation coordinates match a recent authenticated pickaxe trigger. Fail closed on missing, malformed, delayed or ambiguous evidence. Bound per-actor triggers, rates and decoded arrays; clear transient evidence on pause/world change/failure. Observe accepted Silver mining fields and native destruction without modifying traffic, health or terrain.

### Resource publication spacing

ResourceMarkerHideDistanceMeters defaults to 10 horizontal metres, accepts 0–100 and uses zero to disable hiding. After all generated portal/resource/dungeon/runestone/spawner/structure records have passed selected exclusions and their publication callbacks, hide only generated ResourceOwner pins whose final XZ lies at or within the configured distance of a final non-resource managed publication. Index those remaining portal/dungeon/runestone/spawner/structure publications in horizontal cells and query neighboring cells; resources never become blockers. Do not consider unpublished/suppressed dungeon neighbors, excluded sources, disabled catalogs or ordinary personal pins. Compare marker/group publication positions, not individual deposit positions or heights. Apply hiding before the combined pin-count bound and serialization; stale service-owned uploads are replaced by the same accepted filtered catalog. Leave exploration, resource stores, cluster membership, health/depletion observations and issued publication history intact. Reconcile from the current catalogs each time so a resource can reappear after a blocking marker is removed or disabled, without rediscovery. Unchanged output remains byte-idempotent.

### Dungeon pickup progress

DungeonLootProgress defaults true. Publish percentages only after a persistent visit established by observed interior entry or a fresh, fully matched inventory scan with a positive total and at least one picked flag. Share this state across players and discovered gateways of the same location. Scans apply only to discovered entrances; known world locations alone never qualify. Never infer visits from exterior proximity, explored terrain, table uploads, missing records, zero pickups, untouched inventories or old progress files alone. Reject inferred visits when the fresh total falls below the established inventory total. Match ready, living, owner-validated finite player positions using native Character.InInterior and Location.GetZoneLocation semantics: query the interior zone for exactly one persistent exterior LocationProxy, require its allowlisted metadata and reject multiple proxies or oversized record sets. Only mark existing discoveries; a later-discovered gateway inherits a sibling visit. Interior observations never reveal terrain, resources or new entrance markers. Continue visit capture when DungeonLootProgress is off.

After a visit, append a short remaining percentage to discovered dungeons with a verified nonrespawning persistent Pickable objective: Surtling Cores in Burial Chambers/Smouldering Tombs, Black Cores in Infested Mines, hanging Fenris Hair in Frost Caves/Howling Caverns, Frost Cores in Winding Tunnels, and ancient gemstones in Mörkhalla. Validate active metadata, persistent ZNetView, nonnull hide-on-pick and zero respawn. Associate saved pickup records with exact fixed-location or saved generated-room pickup transforms; never use exterior proximity as interior membership. Read saved room layouts without generating scenes. SharedMapDungeonLayout requires a four-byte positive room count followed by exactly 28 bytes per room: Int32 prefab hash, three Single position values and three Single Euler rotation values. Convert Euler angles with Quaternion.Euler as native Utils.ReadQuaternion does. Bound the count to 1024, validate complete length and finite transforms before returning any placements, and retain unknown status for rejected layouts. Count actual placed pickups, deduplicate native identities and treat missing/incomplete/ambiguous evidence as unknown. Zero means either every established pickup is picked or a supported inventory is established empty. A completely decoded layout with no objective candidates establishes empty immediately. Randomized candidate sites with zero actual saved pickups require complete successful scans spanning at least 30 seconds after the visit; malformed/missing layout or ambiguous evidence resets that settling period. An empty scan inside that settling period is inconclusive: established progress and its published label remain unchanged. Missing previously established pickups remain unknown even after settling. Sample inventories for discovered entrances before entry to recognize prior visits, but hide all percentages until entry or positive picked-item evidence establishes a visit. Persist accepted progress in the existing entrance store, retaining older format support.

Advance one target per occupied tick, load at most one new room template per tick, cache at most 2048 templates, bound layouts to 1024 rooms/65536 pickup points, and bound sector queries to 16 zones and 65536 returned records. Match generator identities/coordinates and native custom-interior placement before decoding saved room layouts. Require each accepted pickup record to match exactly one distinct layout site; multiple records claiming one site or a record matching multiple sites keep the inventory unknown. Share one interior inventory across a location's distinct gateways. Group changed progress at Info. Debug pickup and layout records are written only when a gateway's result changes and name the dungeon label, location prefab, gateway and entrance position; pickup records add total, picked, remaining percentage, change flag and reason, six per minute. A shared six-per-minute visit stream distinguishes observed entry (location type, observing peer and newly visited gateway count) from inferred prior visits (gateway and verified total/picked counts); repeated samples do not repeat the visit event. A separate six-per-minute layout stream adds room count, actual/expected payload bytes, validity and decode reason.

Reuse controller-owned pickup points, spatial buckets and identity/site sets between scans; pool at most 4096 bucket lists with capacity at most 64 each. Reject unrelated prefab hashes before spatial matching. Determine zero, one or multiple distinct matching sites without allocating a set per world record; repeated identical template sites still count as one site. Preserve scan cadence, complete-inventory decisions and all ambiguity checks.

### Shared player checkmarks and publication

SharePinCheckmarks defaults false. False strips player checkmarks from shared publication while leaving personal maps native. True accepts checked/unchecked transitions from valid allowed uploads relative to the previous accepted table; unchanged stale uploads do not clear authoritative state. Recognize managed markers only by their issued records and stable source identities, never by icon alone. Persist world-scoped checkmarks and publication history in `.pin-state` independently of tables, with world/schema/checksum validation, atomic backup replacement, a 32768-record limit and a 150 MiB input bound. Ordinary pin keys retain exact owner/label/source position/icon; generated keys use reserved owner and stable source identity. Ambiguous issued identities are rejected. Native grey-to-white adoption changes owner before checking: match only a newly owner-changed record with identical label/XYZ/icon whose unique previously issued managed counterpart is absent from the upload. Existing ordinary pins and uploads retaining the original counterpart are not adoptions. Persist bounded adopted fingerprints, route their check changes to the source and omit duplicate adopted copies from shared publication; personal client pins remain native.
