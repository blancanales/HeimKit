# SharedMap specification

## Scope

SharedMap records exploration around usable player positions in a world-specific community map, independently of whether any cartography table exists. It persists that map separately from Valheim's world save and populates native table map data from it. Terrain read from a table enters the vanilla client's shared-exploration layer, which has no individual player owner. Optional player-built portal markers and outdoor metal/Obsidian deposit markers use native pins. Resource discovery is independent of portal synchronization.

The module is independently controlled by `[SharedMap] Enabled`, default true, in the existing HeimKit DLL under `HeimKit.Features.SharedMap`. It requires no client installation. Follow [architecture](../architecture.md), [contributing](../contributing.md), the [supported environment](../server-setup.md#supported-environment) and the [usage guide](../features/shared-map.md).

## Exploration and accepted table data

Read grid size, pixel size, radius and sampling interval from the loaded Minimap component. Match native WorldToPixel rounding and the integer pixel circle with radius ceil(native radius / pixel size). The code's radius initializer is 100 metres; loaded values are authoritative. Reject invalid geometry instead of substituting guessed values. Use the shared peer snapshot, ready joined characters, owner-matching character ZDOs, positive finite health, finite positions and no dead or interior-height state. Do not gate server collection on public player-map visibility or infer a missing character position from a connection reference point. Sample endpoint circles only; teleports never reveal a connecting corridor. Client and server sampling phase and replication delay can differ.

Valid terrain in an existing or incoming table is unioned into the community map, including exploration collected before the mod was installed. Only fully validated native payloads contribute. Do not infer historical travel from a world seed or generated zones. A table's terrain can already include exploration read from other players; no per-player discovery attribution is claimed.

## Community persistence

When no community file exists, perform a first-run import before starting player capture or table hooks. Scan the world's saved cartography ZDO records through the native iterative prefab lookup, including distant tables without loaded scene instances. Deduplicate table identities and process payloads in bounded batches using MaxTablesPerPass. Union fully validated table exploration only; do not import pins into the community store or modify tables during this scan. Skip invalid payloads with one startup summary warning. Save the completed union before enabling gameplay processing, including an empty checkpoint when no valid table terrain exists. A valid existing file, even empty, skips this migration. Interrupted imports must not save a completion checkpoint; retry from tables on the next startup. An existing damaged file or orphaned backup remains a storage failure, not a first run.

Store the community terrain under `HeimKit/SharedMap/world-<world UID in hexadecimal>.map` beneath the loader-provided configuration directory. Identify worlds by native UID, never display name alone. The versioned file contains its world UID, grid dimensions and pixel size, a packed terrain bitmap and a checksum. Grid and world mismatches, unsupported formats, invalid lengths, corruption or unreadable stores disable SharedMap independently; never silently replace an existing store with an empty map.

Save dirty data at SaveIntervalSeconds and flush on empty/unavailable presence, world or geometry replacement, failure and shutdown. Write a unique temporary file in the same directory, flush it, then atomically replace the destination while retaining its previous contents as `.bak`. A failure must preserve the previous destination. Unchanged masks produce no disk write. A crash or power failure can lose observations since the last completed save. Backing up the world alone does not back up this separate file; recovery must preserve the matching world and community map together.

Retain the accepted mask across ordinary controller pauses. On world replacement, flush the old store before loading another world. A sampling-radius or interval change may reuse stored pixels when grid dimensions and pixel size still match. Incompatible grid geometry must not reinterpret or erase persisted data.

## Automatic portals

`PortalMarkerSync`, default true under SharedMap, independently enables portal markers while the module is enabled. The controller snapshots identities from the native ZDOMan.GetPortalList registry at each TableIntervalSeconds pass, covering native portal prefabs without loading scenes. Resolve each identity against the current world on normalization, requiring a nonzero Piece creator, finite exterior position and membership in community-explored terrain. Read the accepted ZDOVars.s_tag, not the earlier client rename request. Use the current tag as the name, or `NoName` when blank. Connected and unconnected endpoints both qualify; identical tags at distinct locations remain distinct markers unless grouped by distance. New portal identities are discovered by the next pass; changed or destroyed records are revalidated during each table normalization.

Table normalization replaces the managed portal-marker set with the current canonical set, removing stale names, positions, deleted endpoints and duplicates, including stale managed pins reuploaded by clients. Reserve the nonzero owner ID long.MinValue for generated portal pins; it identifies shared service pins rather than a real player or table network owner. Use the native portal-shaped Icon4 marker, empty native author and portal tag as the label, without a special text prefix. While enabled, treat every Icon4 pin as portal data regardless of owner or text, replacing those records from the authoritative catalog rather than trusting their name or position. Other icon types retain their original records except when their label matches a current generated portal label without regard to case and their position is within three horizontal metres of that publication; remove those obsolete portal duplicates on reconciliation and incoming writes. Portal-icon pins used for a different purpose are consequently excluded from shared table data while automatic portals are enabled. Disablement removes service-owned generated portal markers during normalization, preserves player-owned pins including portal icons, and retains terrain/death filtering. When never used, leave exploration-only tables in their native exploration-only format.

PortalClusterDistanceMeters defaults to 60 metres, accepting 0 through 100; zero disables grouping. Process eligible portals in stable native-ID order and assign each to the nearest existing group's first portal within the configured horizontal distance, with stable first-group tie handling. Anchors never move and membership does not follow transitive neighbour chains. Emit a single `Multi Portals (N)` pin at the arithmetic centre of each multi-portal group, including height; a single portal retains its tag. A group may span twice the anchor distance. Same-name endpoints outside a group remain separate. Rebuild groups from live records so renaming, removal, movement and changed eligibility replace the table's previous group representation.

Persist portal source data through the native world records rather than adding pins to the separate terrain file. Reconstruct managed markers on controller activation after restart or reconnect. Catalog refresh, normalization and hooks remain occupied-world responsibilities; no portal processing runs under the first-run offline terrain import exception. Reconcile nearby tables at the existing bounded cadence and normalize incoming accepted table fields. Bound generated portals to 4096, total pin records to 8192, and retain existing payload/string limits. Exceeding a limit must preserve the table rather than write a partial catalog.

Native Minimap.AddSharedMapData only reconciles shared pins when payload format includes pins. Preserve an existing table's format; upgrade exploration-only data when portal pins are added. A format with a zero pin count allows removed managed pins to disappear on a subsequent vanilla read. Vanilla HavePinInRange can retain a pin already within one metre without updating its text. Correct table data does not promise replacement of a personal pin or immediate rename/removal on a client; no custom client controls or forced reads are available.

PortalMarkerSync defaults true. Keep the actual portal/group coordinates separate from published marker coordinates. A new marker starts at the real position. When its label changes, advance through nine bounded publication slots: the centre and a two-metre grid around it, with a maximum horizontal displacement of approximately 2.83 metres. Select a slot whose published position is more than 1.1 metres from the previous publication. Stable portal identity, or the first portal identity for a group, owns this state. Unchanged labels retain their slot across table writes, controller pauses and restarts. The rename workaround is always active while PortalMarkerSync is enabled; disabling portal markers retains the saved publication state.

Persist current names, slots and last published coordinates in a separate world-specific `.portal-pins` file beside the terrain file. Use bounded, fully validated, versioned/checksummed records, flushed temporary writes, atomic replacement and `.bak` retention. Missing state starts empty; malformed/incompatible state or an orphaned backup disables SharedMap rather than silently replacing it. Dirty saves and lifecycle flushes share the existing save-management exception; publication selection remains occupied-world work. Prune identities no longer in the current eligible catalog and bound retained records to 4096.

This is a server-only workaround, not delivery acknowledgment. Vanilla should add a sufficiently separated renamed marker and remove the unmatched old shared pin on Read Map. Native proximity matching ignores the incoming label and icon: an existing saved pin may be retained without either value being updated. Client pin histories therefore produce different visible outcomes from the same table. Nearby personal/other pins can still block insertion; personal pins are not forcibly deleted. Local duplicate removal followed by another table read may be necessary; server cleanup is not a guarantee of per-client replacement. Clients skipping enough renames to encounter a reused slot, deleted/recreated identities and regrouping can also retain a stale label. Height changes do not bypass native horizontal matching. Never move a portal object or modify unrelated world fields to refresh a pin.

Portal changes share the existing grouped table-change Info results. Debug summaries identify the current eligible portal-marker count and whether automatic portal publication is enabled; unchanged scans remain quiet except for existing bounded summaries. Failures remain independent of debug.

## Automatic resource deposits

ResourceMarkerSync defaults true. Its supported types are Copper, Tin, Silver, Obsidian and static Flametal deposits. Use only exact allowlisted native prefab families with validated mining/drop components: rock4_copper and MineRock_Copper; MineRock_Tin; silvervein and rock3_silver; MineRock_Obsidian; MineRock_Meteorite, including supported fractured successors. Dungeon/interior records, scrap piles, giant weapons/armour, creatures and Leviathan sources, dropped/pickable items, player-built objects and ordinary stone are excluded. An asset's presence does not imply that it naturally generates in every world. Gold remains excluded.

Read native ZDO positions and replicated health without loading scenes, instantiating prefabs, taking ownership or modifying deposits. Validate loaded prefab metadata and supported successor/drop relationships before accepting each family. Missing/incompatible families are excluded with one grouped warning; other supported resources and portal processing remain available. Usable character rules and the native sampling interval/radius are shared with exploration. Discover only deposits within the sampled player's horizontal exploration radius; do not interpolate travel or use accumulated exploration as the default discovery source. Silver is an exception to proximity discovery: it remains hidden until a qualifying player pickaxe impact occurs near the actual vein position or a pickaxe hits the eligible Silver vein directly. A direct hit selects that vein without a centre-distance requirement and saves it once; later hits update the same discovery. SilverDiscoveryRadiusMeters defaults to 10 horizontal metres (1 through 30); select only the nearest undiscovered, nondepleted eligible Silver vein, breaking ties by native identity. Use actual source coordinates, never a grouped/publication coordinate. Previously explored terrain cannot unlock Silver. A discovered Silver vein and its fractured successor share one persisted discovery flag. Earlier discovery files have no such evidence: retain their Silver records but exclude them from publication until a qualifying impact. Group only unlocked Silver discoveries. Native generation and replication can delay observations.

ResourceDiscoverPreviouslyExplored defaults false. When enabled, occupied-world bounded iterative native-prefab scans may also discover remaining eligible records in the persistent community-explored terrain, including imported exploration. No terrain is generated or loaded by these scans. Turning the setting off stops retrospective discovery; discoveries already accepted remain retained. Ordinary travel continues to discover newly observed deposits independently of this option or table existence.

Persist source discoveries and the last observed mining-section counts in a separate world-specific .resources file. Read the earlier discovery format without inventing progress, and save extended records only after a real change. Assign monotonically increasing discovery identities; native ZDO IDs are session bindings only because native loading reassigns them. Reassociate the same resource family at its saved position conservatively; ambiguous matches remain unknown. Keep confirmed depleted records as anchors/tombstones so a Tin group's anchor survives mining and session changes. Missing records, invalid health and unloaded instances do not establish depletion. Destructible replacements by fractured mining prefabs continue the original discovery. Retire only terminal records explicitly destroyed by native ZDO destruction or complete validated mining health showing all sections depleted. ResourceRemoveDepleted defaults true; false keeps historical discoveries in publication. Destruction establishes removal, not proof of mining rather than administration. Removal outside active observation can remain unknown after restart.

ResourceClusterDistanceMeters defaults to 30 metres, accepting 0 through 100; zero disables grouping. Stable discovery-order anchors group only the same resource type, using the shared fixed-anchor grouping algorithm without transitive chains. Include retained depleted anchors when constructing groups, but count/publish only remaining records unless ResourceRemoveDepleted is false. A multi-node Tin group uses Tin (N), one node uses Tin and no remaining nodes produces no marker. Count deposit records, not ore quantities or collider fragments. Copper and Silver labels use Copper N% and Silver N%, respectively, calculated as the ceiling of 100 times the sum of remaining mining sections divided by the sum of original sections across discovered deposits in the fixed group. Include confirmed depleted deposits in this denominator and give them zero remaining sections, so removing one boulder does not inflate the group's percentage. A positive remaining section never displays zero percent. Intact Copper/Silver uses its validated fractured successor's section count and starts at 100%; partially mined deposits use all saved sections, including buried ones. This measures remaining mining sections, not volume, exposed surface, damage-to-completion or predicted ore yield. Unknown section totals produce the resource label followed by ?% rather than an invented number; unavailable observations preserve the last valid progress. An all-confirmed-depleted historical group displays the resource label followed by 0%. New discoveries can raise a group's percentage by adding new untouched sections. No below-ground label is inferred: native ground-height queries depend on loaded physics and section health contains no burial flag. Other resource groups use their short resource label. Publish at the active members' arithmetic centre. Counts include discoveries only; unknown nearby deposits are not inferred.

Use native dot Icon3 and the separate reserved owner long.MinValue + 1. Replace only resource-service-owned records; never reserve every dot or delete a player's pin merely because its label matches a resource. Keep portal and resource owners distinct, including portal labels that match resource labels. Reuse managed table-pin reconciliation and persistent publication-slot selection across both subfeatures. Resource publication state lives in .resource-pins; the portal store retains its existing format/path. Count changes select another bounded nearby publication slot, more than 1.1 metres from the prior publication and at most about 2.83 metres from the current centre, to encourage vanilla replacement. This cannot guarantee replacement of personal pins or stale client histories. Read Map remains required.

Bound persisted discoveries to 65536, generated markers to 4096 per source and total table pins to 8192 with existing byte limits. Exceeding a bound must report failure and retain prior table data rather than publish a truncated catalog. Native iterative scans advance one prefab step per tick, process at most 256 matching records per tick and repeat completed passes no faster than TableIntervalSeconds. Ordinary sampling uses nearby native sector records and a rotating per-player candidate budget; no scan may use old explored terrain as travel evidence. Resource grouping/publication caches rebuild only on accepted changes or configuration changes.

### Silver discovery observations

Use the shared Plugin-owned routed-message subscription service independently of AFK tracking. Observe authenticated native pickaxe attack triggers and directly routed pickaxe damage/digging operations without modifying traffic or its cursor. Validate the character owner, health, position, currently equipped pickaxe metadata, target, impact coordinates and nearby player distance. An air swing alone never unlocks a vein. Direct terrain requests must identify the validated native pickaxe dig operation and a terrain-compiler target. Direct damage must identify Pickaxes skill, positive pickaxe damage and the authenticated character as attacker.

Client-owner mining may execute an RPC locally. Cover that path by comparing fully validated old/new terrain-compiler data after accepted ZDO deserialization: operation count must advance, terrain height must decrease and the last-operation point must match a recently observed pickaxe trigger from a nearby currently usable player. Observe accepted changed Silver mining fields/replacements with the same recent-trigger correlation as a direct-vein fallback. Retain no terrain edits; restore packet cursors; never install hooks or subscriptions when resource sync is disabled. Malformed, absent baseline, delayed or ambiguous observations fail closed. Terrain baseline gaps can require another impact; simultaneous nearby tools can make attribution uncertain, so this is server-side correlation rather than a client-confirmed discovery event. Cap per-actor pending triggers, processing rates and decoded terrain arrays; clear transient evidence on pause, world changes or failure.

### Player-service integration

Resource scanning, depletion observation, grouping and publication belong to SharedMapController's existing occupied, native-ready lifecycle, with no additional presence census or AFK lease. Dispose the native destruction subscription and transient session bindings before acknowledging empty/unavailable presence. The module retains accepted discovery/publication stores across pauses. Only dirty saves and lifecycle flushes of accepted data use the existing save-management exception; retrospective discovery is not an offline exception. ResourceMarkerSync operates independently of PortalMarkerSync; disabling it removes resource-service pins during table normalization while retaining discoveries on disk.

Resource storage follows community-map validation, world identity, checksums, bounded parsing, flushed temporary writes, atomic replacement and .bak retention. Missing stores start empty; corruption or an orphaned backup must not silently overwrite data. Save both resource stores at SaveIntervalSeconds and flush on pauses, world changes, failure and shutdown. Include all stores with the corresponding world backup.

Normal results group new discoveries and confirmed removals once per TableIntervalSeconds reporting pass; empty and unchanged operations stay quiet. Existing table-change results cover publication changes. Debug summaries are capped at one per minute and identify discovery records, the last prepared marker count and retrospective mode; source/publication samples and conflicts remain bounded to six per stream per minute. Diagnostics must not gate discovery, removal or persistence and must not claim client delivery.

Portal publication identities use the exact finite saved prefab/position, with signed zero normalized, rather than native ZDO IDs reassigned on world loading. Sort the catalog by stable identity before anchor grouping. Exclude ambiguous overlapping identity records. On first use of stable identities, recover a legacy native-ID publication only when its actual horizontal location (published position minus its slot offset) uniquely matches within half a metre. Preserve its slot and apply any genuine name change normally. Never associate old history using the current native ID. If matching is ambiguous or absent, start a fresh publication and retain normal client-cleanup limitations.

## Selected table-pin removal

SharedMap includes filesystem-authorized administration for a specific shared pin, independent of portal/resource syncing and DebugMode. Work runs only while its normal controller is occupied and world-ready. Use a world-specific `.pin-admin.request` file beside the community map; it contains one command: `find <exact label>`, `remove <pin ID>` or `allow <pin ID>`. Consume bounded valid requests before execution. Find scans saved cartography-table ZDOs incrementally without loading scenes or taking ownership. Report each matching pin's ID, exact label, icon and position at Info, deduplicating the same pin across tables; cap results at 64 and explicitly report omitted results. Advance at most one native scan step and process at most MaxTablesPerPass table payloads per tick. Preserve existing malformed tables and report the skipped count.

A pin ID is the full SHA-256 of a canonical binary record containing its original owner, exact label, XYZ position and icon; exclude checked state and author so those changes do not evade a selected removal. This identifies a specific named pin at its location, not every pin with that label. Validate finite positions and bounded native records before identification. Native ZDO identities are not persistent pin identities. A removal first atomically persists its ID in the world-specific `.pin-removals` store, then starts a bounded sweep of saved tables using ordinary normalization. Filter that identity from existing fields, accepted uploads and generated marker output. Keep every other pin's raw fields and unioned terrain. Normal table-update results describe completed changes; requested administration reports command acceptance and sweep completion separately, never confirmed client delivery. Missing stores start empty; validate world identity, checksum, complete length and an 8192-ID bound. Use flushed temporary writes, atomic replacement and backup retention. Corruption or an orphaned backup must not overwrite prior data. A failed save must not activate an unpersisted removal. Clear only transient scans on pause/failure/shutdown; persisted rules reload on reconnect. Include the rule store in world backups.

`allow` removes a rule and permits future uploads; it does not recreate a deleted pin. Renaming, moving or changing the icon/owner creates a different pin identity. This is selected-record cleanup rather than removal of a live resource or portal source. An automatically regenerated marker with a different identity can appear again. Pin administration never deletes native deposits or portals, alters exploration or accesses personal client maps. Readers use Read Map after replication; vanilla can retain their own personal pins or a nearby matching pin. Native Write Map reads the table before uploading. A missing pin owned by another player can be re-imported; a missing pin attributed to the reader is skipped. Local deletion therefore differs by original pin ownership and later stale uploads can restore a table entry. A persisted removal blocks the original table record from returning through later uploads.

## Table initialization and field filtering

A table ZDO exists only after a table is created. While enabled, occupied and world-ready, observe table prefab assignment and accepted ZDO deserialization, and periodically revisit nearby table records. Fill new or empty tables from the community mask as soon as these paths observe them. This initializes data without a player first choosing Write Map. Scheduling and network propagation can still allow an early read of stale or empty data.

Filter only `ZDOVars.s_data` for the exact `piece_cartographytable` prefab. Keep network execution ownership distinct from map-data attribution: do not claim a table, change its creator or rename pin authors. The server sets the sanitized map field, which advances the native data revision and queues ordinary replication. Leave health, damage, repair, placement, ward, rotation, position, destruction and unrelated fields native.

Intercept accepted incoming ZDO contents after native Deserialize within an authenticated RPC_ZDOData call from a ready peer. Retain the previous map field before deserialization. Sanitize the accepted payload before the RPC completes. Also filter server-local writes to the same byte-array field. No interception of the earlier routed MapData request is required. A native revision rejected as old is not treated as a newly accepted write. A locally handled client write is covered when its resulting ZDO reaches the server. Keep hook context scoped and restored through finalizers, including nested calls and original exceptions.

Remove Death pins, apply selected pin-removal rules and reconcile service-owned portal/resource pins as described above. Retain every other supported pin's original raw record, including owner ID, author, label, checked state and position. This removes shared death entries, not the player's personal death marker. Terrain has no synthetic player owner. Existing valid table exploration and valid incoming exploration are preserved through union with the community mask. Empty tables without generated markers use native exploration-only data, avoiding unnecessary pin reconciliation. A native table payload with pins retains its native format and surviving records.

Validate compressed and decompressed limits, exact grid length, boolean bytes, pin counts, bounded UTF-8 labels/authors, finite positions, supported pin types, complete structure and trailing data before importing exploration or changing table data. Unsupported/malformed incoming payloads do not enter the community store: retain the prior field, or remove an invalid new field if none existed, while leaving other accepted properties untouched. Malformed data already on an existing table is left intact for operator review rather than replaced speculatively. Incoming processing must not bypass native packet or revision handling.

Native table data remains replicated state, not an acknowledged transactional editing protocol. The owning client may briefly see its unsanitized local write until a newer server revision arrives; the server cannot prevent an already completed local read. SharedMap normalizes accepted server state and its later replication, without promising an atomic read/write across peers. Native Write Map first reads the table and then uploads saved personal/shared pins other than native death exclusion. Selected pin-removal rules filter the accepted table record and subsequent reuploads; they do not edit personal maps or provide per-player sharing controls.

## Lifecycle and ownership of resources

Follow the [required player-service hookup](../architecture.md#required-feature-hookup). Plugin injects its existing PlayerServices. SharedMap owns the presence registration, world mask, discovery store and both marker-publication stores. SharedMapController owns sampling, portal/resource discovery, grouping, table scans, table-field normalization, selected-pin administration, its Harmony registration and native resource-destruction subscription. SharedMapMarkerClusters, MapMarker, SharedMapMarkerRefresh and the table-pin writer/reconciler are reused by both subfeatures; eligibility and depletion stay source-specific. Native readiness requires dedicated-server world services, scene, routing and a usable Minimap component. Check native method signatures before activation. There is no AFK lease or feature-local presence census.

Empty or unavailable presence removes all table/gameplay hooks and controller state before acknowledging the pause, then flushes accepted dirty terrain without scanning or publishing. Retain the presence registration and store for reconnect. Readiness loss removes the controller. Shutdown, rollback and failure clear owned references and isolate cleanup steps, without disposing shared player services or another feature's hooks.

Persistence runs independently under the architecture's backup/save-management category, triggered by dirty-save timers and lifecycle flushes of accepted data. First-run import is a separate intentional offline world-processing exception triggered only by an absent community file once native world services are ready. It reads existing table records and saves its completed result even while empty or presence is unavailable. It never samples players, mutates world fields or installs hooks. Ordinary table scans and gameplay remain presence-dependent.

## Configuration

| SharedMap setting | Default | Rules |
| --- | --- | --- |
| Enabled | true | Independent module switch; restart after edits. |
| PortalMarkerSync | true | Maintain player-built portal markers and normalize all portal-icon uploads; disabling removes service-owned generated pins during normalization. |
| PortalClusterDistanceMeters | 60 | Horizontal anchor distance for one Multi Portals marker; 0 to 100 metres, zero disables grouping. |
| ResourceMarkerSync | true | Record outdoor Copper, Tin, Silver, Obsidian and static Flametal deposits independently of portals. |
| ResourceDiscoverPreviouslyExplored | false | Also discover remaining deposits in previously community-explored terrain without a revisit; existing discoveries persist either way. |
| ResourceClusterDistanceMeters | 30 | Fixed-anchor horizontal grouping distance for same-type deposits; 0–100 metres, zero disables grouping. |
| SilverDiscoveryRadiusMeters | 10 | Horizontal radius around a validated pickaxe impact that can unlock the nearest Silver vein; 1 through 30 metres. |
| ResourceRemoveDepleted | true | Hide confirmed removed/depleted nodes; false retains historical nodes. Missing/unloaded state never establishes depletion. |
| TableIntervalSeconds | 10 | Nearby reconciliation interval, 2 to 120 seconds. |
| MaxTablesPerPass | 1 | Maximum table payloads per first-run import tick or periodic reconciliation pass, 1 to 8. Incoming accepted writes and new-table callbacks are handled at their native event boundary. |
| SaveIntervalSeconds | 60 | Dirty community-map save interval, 10 to 600 seconds; lifecycle flushes do not wait. |
| PinDebugNameFilter | empty | Exact label for per-pin Debug detail; empty samples all labels. Counts include all labels. |
| DebugMode | false | Shared global-or-feature policy and manual-only hidden suppression. |

The central loader owns settings creation/preservation; reference defaults stay synchronized. Exploration radius and interval come from the native component. See the [debug configuration contract](../server-setup.md#hidden-per-feature-debug-suppression). Configuration changes require restart.

## Logging

Normal output includes enablement, native-service Ready and isolated compatibility/storage failures. First-run completion emits one summary of tables found, valid payloads imported and saved explored pixels, including an empty checkpoint. Invalid startup payloads produce one separate warning at completion. No per-table startup messages are emitted. Group actual table-field changes and removed death-pin counts once at each periodic pass or completed incoming packet; unchanged and empty operations stay quiet. A field-change notice describes server state, not proof of a client read or delivery. Persistence success is counted only after completed replacement and remains optional Debug evidence; storage failure is immediate and independent of debug.

SharedMapDiagnostics reports one Info storage decision at world/store initialization: existing data loaded with its explored-pixel count and import skipped, or absent data starting first-run import. Loading failures retain the existing error path. Optional Debug details identify the world UID, file path, existing-file decision and loaded pixel count. Player reconnects and ordinary scans do not repeat this initialization evidence.

SharedMapDiagnostics also owns optional geometry, current pixel counts, latest-pass sampling/table scope and bounded invalid-table warnings. Existing malformed tables and rejected incoming map fields retain distinct warning meanings. Shared player services own occupancy notices. Debug suppression never gates terrain collection, death filtering or saving.

Bound publication selection and actual table-field evidence to six Debug records each per minute. Publication details identify stable marker identity, old/new label, real/published coordinates, slot and distance from the previous publication; they do not establish a client read. Table details identify object ID, native data revision and accepted-client, nearby-reconciliation, prefab-assignment or server-field-write boundary. Summary counters distinguish pixels added by player circles from pixels imported through tables, accumulated since the current controller started and reset on recreation. Refresh-state load/save evidence stays Debug; storage failures remain visible independently of debug.

Optional pin-change Debug evidence compares validated previous, received and final table pin lists independently of whether normalization changes the received bytes. Report additions, removals and checked/author changes; represent renames, moves, owner or icon changes as removal/addition rather than guessing player intent. Preserve duplicate multiplicity. Each comparison reports its table/revision, stage and added/removed/updated totals. Per-pin details include exact label, XYZ, icon, original pin owner, checked state and author. Capture the authenticated replication peer ID and character name when available, labelling that peer as the sender rather than claiming it clicked Write Map; a table-owning client can replicate another player's write. Server-local writes have unknown sender attribution. Log ordinary accepted pin-list changes even when HeimKit normalization leaves them unchanged. Pin data missing from the received update demonstrates a server-observed removal, not a directly observed client click. No logs claim personal-map state, Read Map delivery or confirmed player intent.

PinDebugNameFilter defaults empty and limits only per-pin Debug detail to an exact case-sensitive label when supplied; counts still cover all changes. Respect the shared effective Debug policy before decoding pin snapshots. Bound comparisons to 60 per minute, summaries to six per stage per minute and details to six per stage/action/source-family per minute, separating player-owned and generated pins so automatic updates do not consume player-removal samples. Track omitted comparisons/details through the existing omitted-evidence counters. Debug failures are isolated from normalization, persistence and native traffic. Invalid comparison snapshots produce bounded Debug evidence and do not invent removals; existing payload rejection remains independent. These are sampled diagnostics, not an exhaustive audit trail.

## Deferred scope

Other resource/location families and selective private-marker sharing remain outside scope. Resource retrospective discovery requires its explicit optional setting. No client-side controls or conversion of shared terrain into personally explored terrain are included.

Portal catalog Debug summaries report registered records, eligible explored portals, excluded records, resulting grouped marker count and clustering distance, bounded to one summary per minute. Separate removal details identify a marker's identity and prior label when it leaves publication state because it is no longer eligible or has regrouped, bounded to six records per minute. Removal evidence describes server publication state, not confirmed client cleanup.

Catalog summaries identify persisted community exploration as the eligibility source and include the native pin type. Up to six rotating publication samples per minute include marker identity, label, published position and icon type, so stable markers omitted by the initial change-event budget are observable over subsequent scans. These samples do not inspect personal client pins or confirm client rendering.

When Debug is enabled, table normalization reports preserved pins whose labels match generated portal labels without regard to case. Up to six records per minute identify the preserved icon, owner and position alongside the generated portal icon type. The evidence distinguishes removed nearby duplicates from preserved distant matching labels; it does not confirm client rendering.

When cleanup detects an obsolete pin within the native one-metre matching range of the current publication, select and persist a different bounded publication slot more than 1.1 metres from that pin, then regenerate table data. Repeated stale uploads keep the corrected slot. This helps vanilla remove an unmatched old shared dot and insert the portal icon on Read Map; local personal pins remain outside server control. Nearby duplicate cleanup is part of portal management and does not depend on Debug logging.
