# HeimKit Settings specification

The same assembly runs on Windows dedicated servers and Windows game clients. The world host runs the gameplay modules in a private world, a Start Server world or on a dedicated server. The client uses its own `heimkit.client.cfg` and opens HeimKit Settings with F7. Server Settings controls the active host. Label controls that affect only the local game as client-side only and place them under Client Settings. A dedicated server with client support enabled sends feature status after a client opts in.

Client Settings exposes a separate, default-off TameTravel debug switch. It applies immediately on the observing game installation in either hosting role. Match the local character and original animal IDs across native command, gateway, player completion and destination scene observations. Log both scene and network record positions. With departure animals under observation, the client samples the floor beneath the traveller on arrival and again three seconds later if observation continues. The destination_floor event identifies the floor and overhead collider, their network IDs when available, the floor height above terrain, the vertical clearance at that point and the watched animal IDs. A missed upward probe reports its twelve-metre range. Identify unobserved departure animals as scene observations, including nearby bystanders. Server feature debug continues to control the host log independently.

## Live server diagnostics

Under Server Settings, a shared Server Diagnostics section shows the active world's Diagnostics entries for global debug logging, Normal or Verbose output, and the sampled object interaction trace. Keep feature debug switches with their features. Selecting Verbose allows any feature with effective debug logging to emit its detailed records. A host can enable TameTravel debug alone and switch the shared output level during a session.

Use the existing host settings channel, validation, request limits and acknowledgement. Bind the three controls to the active host configuration. Accept only their documented keys, booleans and verbosity choices. Recheck the local world-host role or the remote physical connection's admin status and AllowAdminChanges at apply time. Read back the host value after persistence and report a failed write. Compatible clients display the values the host advertises. Vanilla guests need no client component.

Apply changes without reinitializing gameplay modules or interrupting transfers. Reconcile the host interaction observer when its effective debug policy changes, install it at most once, and dispose it on disable or world shutdown. Keep the existing sampling, suppression and output budgets. Log administrative changes once with actor, setting and outcome. These operations require no world-object search.

Acceptance requires that a host or permitted admin can change and restore verbosity during an active session, see the confirmed value after reopening F7, and recover the saved value after restarting the world. Ordinary guests and admins with remote edits disabled cannot change the host settings. A client connecting to a host without this capability sees only the supported controls.

## Player-hosted worlds

On dedicated deployments the optional game client supports administration and performance diagnosis. Client Settings exposes a local, default-off interaction trace. For container opens it observes the local interaction, owner request handler, open response and inventory open/close boundaries. Correlate client Debug samples with host observations by object ID, requester and time. Turning the switch off removes the observer hooks. The switch admits these Debug samples to the client disk log independently of the loader severity filter. If there is no disk listener, a local interaction log receives them.

F7 distinguishes a private local world, a world opened with Start Server and a remote server. Both player-hosted modes expose all gameplay modules to the player hosting the world. The local configuration is populated with the same defaults as on dedicated servers.

A player host is the game client acting as Valheim's world server. Use the native session role and current world identity to authorize the host's settings changes in process. Wait for the local character and world services before reporting features ready. Revoke access, discard pending edits and dispose the gameplay session on exit or world replacement. Guests can join through Valheim and experience supported gameplay features from the host. They have no F7 access to the host configuration. Remote F7 settings and admin status come from the authenticated dedicated server connection.

Use the same module host and setting catalog in both hosting modes. Share setting validation, persistence, application boundaries and status reporting. Remote requests retain native admin authorization through the physical connection. Local requests verify the current host and world directly. Local gameplay configuration lives in `BepInEx/config/HeimKit/Worlds/<world-id>/heimkit.cfg`. The shared loader creates it on first use and preserves existing values. The runtime uses the world identity supplied by the live Valheim session. It opens the local HeimKit configuration and relies on Valheim for world saves, whether the world is stored on disk or in the cloud. Local F7 preferences remain separate.

The shared player services must expose the local character as an actor without manufacturing a network peer. World scans, activity and clearance consume actor observations. Only transport operations consume authenticated network peers. Use the native local ownership and completion path where no network handoff is needed. Player-hosted worlds isolate module failures for the current session. Dedicated servers retain their startup backup and persistent failure protection. Player-hosted worlds use a soft 1.5 ms frame budget for cooperative work and a separate soft 0.5 ms WeatherGuard protection slice. Global Verbose Debug enables the shared performance window and slow-stage reports for hosted frames.

| Gameplay capability | Local hosting requirement |
| --- | --- |
| DoorKeeper, ForestRenewal and SeaSalvage | Use the local actor for discovery and clearance. Preserve native interactions and confirm world changes and persistent records. |
| InfiniteTorches, WeatherGuard, StationSupply and HeimMender | Resolve local ownership and use the native local execution path. Preserve checks, atomic state changes and confirmation. Do not wait for acknowledgments from a nonexistent peer. |
| AFKNightWatch and AFKRaidWatch | Observe the local actor and local input for activity. Preserve native bed, time and raid rules. |
| SharedMap | Capture the host’s native exploration and reconcile local map reads and writes against the active world’s community data. Guests use native table interactions and the shared server-side filters. |
| TameTravel | Observe native host commands and accepted portal travel. Use native arrival and scene readiness for the host, and retain authenticated guest observations and ownership drains. |

## Transport and state

Protocol version 2 uses one ZPackage per message. Objectless `HeimKit_Hello` carries the protocol and client version. `HeimKit_Set` carries a request ID, module, setting key and either a one-byte boolean or an eight-byte little-endian numeric value. The payload length distinguishes the two types. Both are routed to the server peer. The server matches the envelope to the ready physical connection. It sends `HeimKit_State` directly on that connection, with protocol and server version, revision, admin flags, the recipient's request result and all switch and numeric setting entries. Numeric entries include the server value, minimum, maximum, whole-number requirement and application note. A mismatch response contains just the protocol and server version. Text is UTF-8 with a 16-bit little-endian byte count. Status, reason and result codes occupy one byte. Pending values use 0 for absent, 1 for false and 2 for true.

Packages are limited to 16 KiB and 256 entries. Module names, keys and labels have a 64-character limit, descriptions 200 and versions 32. Decode errors are bounded warning incidents. The server retains at most 256 clients and 64 queued requests.

| Client link | Policy |
| --- | --- |
| Out of world, checking or version mismatch | Client modules stop. |
| Client only | Local settings govern modules that can run independently. Existing server modules require a HeimKit server. |
| Server explicitly disabled client support | Client modules stop. The menu still shows connection details and local preferences. |
| Connected | A paired server module must be on and its local switch enabled. Disabled and unavailable server modules suppress their client parts. |

The client registers on its server connection before sending Hello. It refreshes connection state once per second, retries Hello at five-second intervals and clears state on departure. A later valid reply can establish a connection after retries expire. Older revisions are ignored. A single setting request can wait five seconds for its first result and up to 75 seconds for completion after a pending response.

The client sends a direct HeimKit_Identify message on the authenticated game connection immediately before the native character ID. The server registers this handler when the peer connection is created. With client support disabled, the server answers only identification with a direct HeimKit_Disabled notice carrying its version. It sends no feature status or admin controls. A server that sends no recognized response leaves its support status unknown. The per-character Info join line reports a HeimKit client with its reported version and any protocol mismatch, vanilla when no identification arrived, or detection unavailable when client support is disabled. An older client can still be confirmed by its first valid routed Hello. Retries stay quiet at Info.

## Player moderation

The host records character entry from the shared joined-world presence service, independently of F7, client identification, admin occupancy and remote client support. The local host enters on the first valid local character in that world session. Death preserves the session. A durable account directory retains the latest observed name and UTC join time by authenticated socket identity or local platform identity. A session without an account identifier remains visible with a non-actionable session identifier. Online membership is transient. Dedicated history belongs to the server configuration directory and local history to the active world's configuration directory.

A compatible dedicated client receives ordinary settings through the existing handshake. The host delivers moderation separately on the authenticated admin connection and rechecks native admin membership at delivery and action time. Revocation discards the client's roster, bans and pending confirmation. The local host reads and acts directly in the current world. Guests receive no moderation updates. AllowAdminChanges governs remote actions independently of viewing. Ban confirmation fixes the account ID and unban confirmation fixes the exact native entry. The host validates the target against its own history or current native list, then updates Valheim's synced list and leaves enforcement to the game.

## Administrative changes

For remote requests, the server checks `[Client] AllowAdminChanges` and the native admin list using the physical socket’s host name. In-process requests use the current local host and world check. Both paths check the rate limit of ten requests per ten seconds, the module’s setting catalog and failure protection. Numeric values are allowlisted by the owning module. The server rejects non-finite, out-of-range and fractional values for every numeric request before writing. All exposed numeric settings update live without an idle hold or module reinitialization. Each feature guide explains when its new value takes effect. Equal values succeed without writing. Applied values save through the server configuration and are included in the next full snapshot. Admin identity, applied values and pending or busy outcomes are logged at Info. Rejected non-admin requests are bounded warning incidents. Protocol diagnostics use the control topic.

`ModuleHost.Reapply` pairs setting changes and reinitialization inside `PlayerPresenceEvents.AdministrativeChange`. Deliberate disposal leaves the current occupancy announcement intact. Genuine activation failure prevents an unearned aggregate announcement. Each feature exposes its existing `DebugMode` as an independently live switch. It uses the same server authorization and audit log as gameplay switches, saves to the server config and skips reinitialization and idle holds. The shared debug policy still decides effective logging. HeimMender reconciles its own live settings on its next tick inside an administrative scope. WeatherGuard applies rain and underwater changes in place while at least one channel remains enabled. SharedMap applies portal markers, discovery of resources and dungeons in explored areas, removal of depleted resources, player map writes and shared checkmarks in place after its idle boundary. HeimDefender reconciles its server switches through its occupied-world controller. The personal SharedMap preference and both new client traces apply within the player's game. Other gameplay switches use their existing lifecycle.

StationSupply, TameTravel, SharedMap, SeaSalvage and ForestRenewal can defer a reapply. One pending request per module holds new work and gives current work up to 60 seconds to finish. A second request for that module or a timeout reports busy. Failure, world replacement and shutdown release holds and discard pending requests. Changing WeatherGuard’s Enabled switch or crossing the all-off protection boundary reinitializes WeatherGuard. A TameTravel reapply can clear follow state.

| Module | Admission during hold | Idle boundary |
| --- | --- | --- |
| StationSupply | Pause transaction discovery after servicing active transactions and queued manual requests. | No active transactions, retained leases or queued manual requests. |
| TameTravel | Pause portal entry and follow-spacing acquisition. Release existing follow-spacing control while journeys drain. | No reserved followers, transfers or authority leases. |
| SharedMap | Pause periodic discovery and new table reconciliation. Advance current table work and request saves without waiting for the regular interval. | No bootstrap or table work and all stores clean. |
| SeaSalvage | Pause cargo recovery after checking destruction of consumed drops. | No retained consumed source records. |
| ForestRenewal | Pause new renewal intake and placement while polling the ledger and advancing the current placement. | No placement, dirty state or outstanding ledger write. |

## Player-service integration

Control is an explicit administration and access management exception. It neither registers a presence consumer nor participates in aggregate notices. It subscribes to the shared routed observer while players are joined, dispatches its bounded queue on a one-second timer, and coalesces broadcasts on that timer. With no joined players, the control observer releases its subscription. It performs no world scans and uses the existing shared routed patch target.

A separate client Harmony instance is installed on first menu open. While the panel is open it hides the native aiming and bow reticles and restores their previous visibility on close. It captures the camera cursor, both gameplay input predicates and pause-menu update. The panel also consumes Valheim wheel input over the settings pane and suppresses camera wheel zoom while open. Native inventory, map, console and chat can open independently and close the HeimKit panel. The Unity UI dialog scales within an inset from the viewport edges. Embedded artwork supplies a carved banner with the HeimKit shield and wordmark, button textures, timber, bronze rails and module icons. The panel uses dedicated backgrounds for scope tabs, feature rows, Close and Apply. Labels use the Valheim TextMesh Pro font, feature icons sit inside their borders, and checkmarks are gold. Server Settings and Client Settings are available to all clients. Authorized administrators also see Server Administration. Server Settings shows the reported module catalog in an illustrated sidebar and the selected module in a scrollable pane. Modules with at least ten additional switches use two columns for switches and full-width numeric controls below. An amber glow follows the selected button's existing rim and fades inward across its face. The status label is white, with green On and amber Off values. The header always shows status. A runtime failure or protection hold shows Disabled after error, with a notice distinguishing a local session hold from dedicated-server protection. Other unavailable states show Unavailable and their reason. Client Settings shows the local menu key and configuration instructions. Object interaction logging and TameTravel debug logging use the same checkbox layout as server switches. Each checkbox displays the saved local value and applies changes immediately. Setting descriptions and the local configuration path are shown using native Settings hover tooltips. Pointer tooltips appear only over the rendered setting label text. They open to the right of the cursor where space permits and stay inside the screen. Dropdowns use the feature-button face and open a bronze-rimmed navy list with ivory labels, amber focus and a gold checkmark beside the current choice. Numeric rows use a bronze-rimmed dark track, gold fill and a faceted gold thumb at the current draft value. Track clicks and thumb drags use the visible track’s local coordinates. Mouse presses anywhere on the visible track or thumb use the overlay cursor position. A drag retains its setting and grab offset across a status refresh and ends on release, loss of focus or loss of edit access. Admins can click the track, drag the handle or type a whole number. Existing fractional values loaded from the configuration remain in effect and display rounded until a new value is applied. Their row tooltip shows the description, configured default, accepted range and when the value takes effect, including in read-only mode. Numeric rows keep additional details in the tooltip. Slider and field edits update a local draft until Apply sends it to the server. Bronze rails separate the settings header, sidebar and footer. The header shows Type, Status, Access and Settings on one line. Server status reports the HeimKit link. A loaded player-hosted world shows Connected independently of feature availability. Type distinguishes Local world and Hosted world. Access is either Admin or Read-only. Settings names the configuration in use or reports why it cannot be shown. The client header identifies the local installation as its scope. The footer shows both versions. Scope changes preserve the selected server module, its scroll position and numeric drafts. The client page is available independently of server support. Its canvas is inactive while the panel is closed. Closed-menu work consists of key polling and the link timer, with no per-frame state formatting. Future client modules have an independent host and failure isolation.
