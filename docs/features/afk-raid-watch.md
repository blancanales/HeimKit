# AFKRaidWatch

Helps protect idle-only locations from new normal automatic random raids. It is an independent Windows dedicated-server feature; clients need no mod. AFKNightWatch separately controls sleep.

Protection uses the native local event range. Every relevant nearby actor must be known, alive, outside beds and inferred idle. Active or uncertain nearby players retain normal eligibility. An active player elsewhere does not remove an idle-only area's protection. Existing raids, explicit/admin, forced/scripted and standalone events continue normally. This does not grant invulnerability or prevent ordinary enemies.

`[AFKRaidWatch] Enabled` alone controls protection and defaults true. DebugMode defaults false. Shared idle thresholds live in `[PlayerActivity]`, defaulting to five minutes idle and one minute join/recovery grace. Detection runs during daylight whenever either enabled consumer needs it. Inferred idle cannot prove human absence; some client-local actions remain invisible. Stop the server before edits and restart. See [configuration](../server-setup.md#afkraidwatch), [specification](../specs/afk-raid-watch.md) and [supported environment](../server-setup.md#supported-environment).

Global or feature debugging follows [hidden suppression](../server-setup.md#hidden-per-feature-debug-suppression). Raid summaries describe actual supplied-candidate evaluations, exclusions and observed event outcomes with ages. Targeted details describe local populations, native gate/hook evidence and start/setter observations; they do not prove client delivery, enemy spawning or causality. Shared PlayerActivity transitions are printed once when a registered consumer permits them; raid debug does not enable sleep diagnostics. Bounded streams follow the [repetition contract](../architecture.md#repetition-and-volume-limits) and [empty-server pause](../architecture.md#empty-server-debug-pause). Empty servers skip HeimKit filtering while native schedulers continue. The specification describes remaining diagnostic incident limitations.

Player-dependent processing pauses when the server becomes empty or player presence is unavailable, and resumes on the first connection once required world services are ready. Additional connections do not restart processing. The feature stays configured Enabled during this pause; native game systems continue. See the [presence lifecycle](../architecture.md#presence-driven-lifecycle).
