# AI build and release versioning

These instructions apply to AI agents working on HeimKit. Read [AGENTS.md](../../AGENTS.md) for project scope and action authorization. This document owns the detailed policy for identifying development DLLs separately from releases.

## Choose the requested workflow

- "Create a test build": prepare a development identity, then use the existing build.ps1 command for one local DLL. Use Release configuration unless Trevor requests Debug. Keep the output in the standard source bin directory. Do not merge, publish or delete the feature branch.
- "Create a release for me": follow the [AI release workflow](releases.md). That actual request includes committing the intended source, merging into main, preparing a plain release version, invoking Build-Release.ps1, pushing/tagging main, publishing the GitHub release with the ZIP attached, and deleting the merged feature branch after success. Trevor uploads the ZIP to Thunderstore. A discussion or quoted example is not an instruction to start this workflow.
- A request for the Release compiler configuration alone remains a local build request. Release configuration and a published release are different concepts.

## Version and authorization rules

- Source edits, development builds and releases are separate actions. Editing code does not request a build, and requesting a build does not request a release, package, publication, commit, push, installation or restart.
- For an explicitly requested test build, prepare the source identity/documentation, then invoke `build.ps1` using [building from source](../development.md#building-from-source). A normal local build creates only the requested configuration; it does not require both Debug and Release or an automated-check build. Verify the resulting DLL identity and report its standard `src/HeimKit/bin/<configuration>/<target-framework>/HeimKit.dll` path. Do not copy development DLLs into a separate versioned artifact folder. A failed compilation may require a corrected rerun. Editing build guidance or scripts does not itself authorize another build.
- For an explicitly requested development or debugging DLL, use a prerelease identifier describing the work and an increasing build counter. Illustrative examples: `0.1.52-sm.1`, `0.1.52-sm.2` for SharedMap, or `0.1.52-weather-fix.1` for a fix. These are naming examples, not declarations of supported or released versions. Use valid numeric major/minor/patch components; put the work label after the hyphen.
- Each changed-code development build receives a new counter in its work stream. Rebuilding identical source may retain its identifier. Do not automatically advance the plain release number for successive development builds or describe a development DLL as a release.
- Keep the published release version unchanged until Trevor explicitly requests release preparation. Choose the intended next release base deliberately; do not infer a minor-version release merely because a feature is being developed. The final release removes the prerelease suffix and uses the agreed release version.
- When a development build is requested, synchronize its full build identity wherever supported in project/plugin metadata, startup output and the documented build identity. Where tooling requires numeric assembly metadata, retain a compatible numeric value and carry the full development identifier in the appropriate version metadata and visible build identification. Do not silently discard the suffix or make different DLLs appear identical.
- Keep Windows Product version equal to the clean development or release identifier, without an appended Git commit hash. Set `IncludeSourceRevisionInInformationalVersion` to `false` in the project. Windows File version remains numeric; build configuration is identified separately in startup output and the standard configuration-specific bin directories.
- Development builds do not require release notes or release packages. Prepare the release changelog and package only within an explicitly requested release or packaging scope. Keep behavior/configuration documentation current with source changes regardless of build or release status.
- This policy takes precedence over older wording in linked contributor/development procedures that implies every changed-code build must increment a plain release version. Apply their synchronization and documentation requirements using the appropriate development or release identity.

Before an authorized build, follow the [contributor preparation procedure](../contributing.md#before-every-build) using this policy's development or release identity. Keep affected behavior/configuration documentation current. Report the exact build identity, artifact location and observed results in the active chat; keep testing instructions and results out of persistent documentation. Without an explicit build request, leave source edits reviewable without compiling or changing version metadata.
