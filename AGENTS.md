# HeimKit contributor instructions

These instructions apply to the entire repository. Follow the user's current task and keep changes within its scope.

## Required reading before editing

1. Read [docs/contributing.md](docs/contributing.md) for the procedure for creating and organizing features. Then read [docs/architecture.md](docs/architecture.md) for file placement, naming, configuration, logging and feature lifecycle rules.
2. Read the relevant feature specification in [docs/specs](docs/specs). For current torch work, read [docs/specs/infinite-torches.md](docs/specs/infinite-torches.md).
3. Read [README.md](README.md) for the overview and documentation links, then the relevant guide in [docs/features](docs/features) for user behavior and configuration. Read [docs/server-setup.md](docs/server-setup.md) and [docs/development.md](docs/development.md) when changing operational or build guidance.
4. Inspect the current implementation and working tree before making changes. Preserve unrelated local changes.

The architecture document is the canonical project-wide design reference. Feature specs define behavior and acceptance criteria. If a spec conflicts with the code, identify the difference and resolve it within the user's authorized task rather than silently assuming the code is correct.

Keep user-facing safety, sampling, inference, replication and delivery caveats in [docs/limitations.md](docs/limitations.md); link to that page instead of repeating disclaimers in every feature/subfeature. Keep feature scope and implementation rules in their owning guides/specifications.

Keep shared documentation independent of any particular assistant, vendor or tool. Tool-specific entry files contain only a pointer to this root AGENTS.md file; project rules belong here and in the referenced documentation.

## Current scope

Use "server side" to mean the world host in solo play, Start Server play and dedicated hosting. Apply the [process role definitions](docs/architecture.md#process-roles-and-live-administration) when planning features. Use the [base rule for all HeimKit features](docs/architecture.md#base-rule-for-all-heimkit-features) for every existing and future feature. Document dependencies per capability and follow the architecture rules for F7 visibility and admin access.

Work locally on the checked-out working branch. The same HeimKit plugin runs in the Windows game and on Windows dedicated servers. The game client provides HeimKit Settings (F7). In a private world or one opened with Start Server, the host also runs the gameplay modules and manages settings for that world. On a dedicated server, a remote HeimKit client can view settings and an authorized admin can edit them when the server permits it. The source contains InfiniteTorches, WeatherGuard, AFKNightWatch and AFKRaidWatch, plus SharedMap persistent community exploration, table initialization and map-field filtering. SharedMap optionally adds player-built portal markers, outdoor metal/Obsidian deposit and Black Marble skull/rib and discovered Ancient Root sap-reserve markers, allowlisted exterior dungeon entrance markers, lore runestone landmarks and persistent recurring spawner markers; DoorKeeper adds optional delayed door closing, ForestRenewal adds optional sapling renewal and SeaSalvage adds optional floating recovery cargo and TameTravel adds validated outdoor portal travel for explicitly following tames. HeimMender adds bounded gradual and administrative repairs for player-built static structures. StationSupply feeds supported production intakes from one nearby public chest each, with independent fuel/material placement and optional fermenter and Obliterator feeding. SharedMap also marks Fuling villages and the additional exterior structure families in its specification. Other location/resource families remain outside scope. Resource markers exclude scraps, dungeon resources and creature sources. Do not infer gameplay guarantees from compilation.

For dedicated deployments, the optional game client serves administration and performance diagnosis. Client-side action and timing evidence can be correlated with host logs. For client UI, hosting, settings or interaction diagnostics, read the [HeimKit Settings specification](docs/specs/client-control.md) and [HeimKit Settings guide](docs/heimkit-settings.md). Identify which process observes each event and which configuration file or F7 control applies. A feature debug switch under Server Settings controls the active host. For multiplayer interactions, consider the requesting client, the world host and the object-owning peer separately, even when one process fills multiple roles.

WeatherGuard priority: automatic weather protection for player-created structures first, preserving their existing creator. Claiming/protecting individual repaired world pieces is secondary. A nonzero creator makes a player-built piece eligible for protection; it must not be used as a protection exclusion. Require seamless activation during play, one normal Enabled switch, and unchanged combat/support behavior. Do not require logout-based activation. World-created claiming is not part of the current implementation.

Only add another feature when requested. Before implementing it, document its behavior and where HeimKit must be installed in a new feature spec. HeimKit supports gameplay delivered by the world host and enhancements delivered by a player's HeimKit client. For each capability, state what the host provides to vanilla guests, what a HeimKit client adds, and whether the host and client must cooperate. Future ideas and incomplete functionality do not belong in the README's feature list. Maintain one current specification per feature; do not create development journals, abandoned-design histories, task-tracking Markdown files or completion checklists. Use README.md to introduce the application, feature benefits and user expectations, compatibility and links to detailed documentation as defined in [docs/contributing.md](docs/contributing.md#update-documentation). List all supported version values only in [docs/server-setup.md](docs/server-setup.md#supported-environment); every other document links there without repeating version values. Put build commands in docs/development.md. Never persist testing instructions, test results or validation-status notes in documents; provide them directly to the user in the active chat, following [docs/contributing.md](docs/contributing.md#testing-information-belongs-in-chat-only). Feature specs describe compatibility behavior without repeating supported version numbers.

## Implementation workflow

### AI action authorization

For each feature that accepts client input, review what an ordinary connected player and an authorized administrator can cause the world host to do. Document the host's checks on identity, permission, target and request bounds. Preserve native gameplay permissions and validate species-specific exceptions against the installed game before extending an interaction through HeimKit.

These instructions govern AI agents working in this repository. Human contributor and development guides describe procedures; they do not authorize an AI agent to perform those actions.

- A request to add a new feature starts with feasibility research and a detailed proposal. Inspect the relevant HeimKit implementation and shared Core services. For gameplay or networking, trace the relevant methods in the installed Valheim assemblies and inspect prefab data where it affects behavior. Identify which process observes each required event and which can authorize and perform the action in private worlds, Start Server sessions and dedicated games with vanilla guests. Apply the project's performance, debugging, security and shared-code rules to the proposed design.
- If a proposed feature appears to require repeated whole-world scans, first check whether a native Valheim event or an existing HeimKit Core service can identify the affected objects. If a cost or gameplay tradeoff remains, explain it to Trevor in chat before implementation: describe how often the work runs, what bounds it, and what players would experience. Record the agreed approach in the feature spec.
- Design diagnostics in the initial feature spec and implement them with the feature. Identify what can go wrong or run slowly, which process can observe it, and what its logs must show to explain the outcome. Capture relevant triggers, decisions and reasons for skipped or failed actions. For performance-sensitive work, pair elapsed time with a measure of the work done. Reuse shared instrumentation and the architecture's debug controls and volume limits. For operations spanning host and client, include identifiers that allow their observations to be matched.
- Present the feasibility finding in chat. Explain at a high level what can be done, where it would run and which HeimKit components would change. Identify any blocker, client requirement or open question and the evidence that could resolve it. In the same review, provide a detailed proposed specification under `docs/specs/` covering player behavior, hosting and ownership, implementation responsibilities, shared services, performance bounds, diagnostics, security checks and acceptance criteria. Incorporate Trevor's requested tweaks into that same specification. Begin implementation from the reviewed specification once Trevor approves it.
- A request to review logs or investigate an issue authorizes read-only investigation and a report. Inspect the available client and host logs, relevant HeimKit code and installed Valheim behavior. Match build, session, time and original object or character IDs where available. Report observed behavior, confirmed code defects and unresolved causes separately. A confirmed defect may still have an unproven connection to the incident. If a fix is identified, follow the proposal and approval rule below.
- For each material unknown, explain what evidence is missing, which process can observe it, and what observation would distinguish the plausible explanations. First check evidence already available, including whether the relevant trace was active during the incident. If more evidence is needed, describe the smallest useful next step in chat, such as an existing log from the object-owning peer, a focused reproduction with an existing trace, or a proposed diagnostic at the code that performs the action. Identify the event and fields to capture and how the result would change the diagnosis. Leave code, settings and live installations untouched during review.
- When Trevor says "fix the issue" and the cause is still unknown, first determine whether a specific test using existing diagnostics can supply the missing evidence. If it can, give Trevor the exact test and explain what to capture. If the test requires new instrumentation, name the component and ask: "I can't fix it without additional diagnostics in place, would you like me to add the additional diagnostic logging to <Component/feature> and create a new build?" Wait for his answer before editing code or building.
- A "yes" to that combined question explicitly authorizes both the proposed diagnostic change and one local test build. Complete both without asking again. Deliver the verified DLL and specific test directions in chat: identify where to run the build and enable the trace (only if needed), the starting conditions, actions to take, relevant player/object IDs or time to note, which client or server logs to provide, and which events will answer the open question. When Trevor makes the post-test logs available, correlate them and report what they establish. If he requests diagnostics alone, build authorization remains separate.
- For every fix, once the issue and remedy are understood, tell Trevor: "I see the issue now and how to fix it, we need to do X". Replace X with a short, concrete description of the change. This applies even if he originally said "fix it" or approved a diagnostic build that later confirmed the cause. Wait for his decision before making the fix. If he approves, implement the proposal. If he denies it, stop that fix. If he asks questions, answer them, revise the proposal if needed, and wait for approval. Build the fix only when the build is also explicitly authorized.
- Do not create a build unless Trevor explicitly requests a build. This applies to blank scaffolds, functional code changes, fixes and documentation work. An instruction to add or implement a feature does not itself request a build. Do not trigger compilation indirectly through automated checks, packaging or another tool.
- Do not increment application versions, change build metadata, prepare release notes or create release artifacts merely because source code changed. Perform the version-and-documentation procedure only when preparing an explicitly requested build or release.
- Leave edits local and reviewable unless Trevor explicitly requests a commit or push. Creating a requested GitHub branch from an existing commit does not authorize committing or pushing subsequent edits. Packaging, publishing, installation and server restarts require their own explicit scope.
- Approval of a tool-access prompt is not a request to expand the task into building or publishing. Establish authorization from Trevor's task instructions before requesting tool access.
- A blank feature addition includes only the requested source structure, independent settings, registration, compatibility and player-service lifecycle, with accurate scope documentation. Keep it disabled by default and do not imply gameplay functionality exists.

### Source changes and explicitly requested builds

1. Use `src/HeimKit/Features/<FeatureName>/` for all files specific to that feature. Do not use the word `Feature` in class or interface names.
   Name feature-owned behavior classes `<FeatureName><ResponsibilityOrAction>`. Model and enum prefixes are optional guidance; prefer descriptive names. Display the chosen feature name exactly, without appended development labels. Follow the architecture naming rule; document limitations separately from the name.
2. Keep plugin entry-point orchestration in `Plugin.cs`. Keep shared contracts/utilities in `Core/` and configuration setup in `Configuration/`.
   HeimKit uses the Core-based implementation under `src/HeimKit/`, governed by [the performance rebuild specification](docs/ai/heimkit-rebuild-spec.md). Shared services live only in `Core/`; configuration remains in `Configuration/`. Feature folders must not own world scanners, prefab metadata caches, native-reflection caches, packet/ownership managers, presence hubs or config loaders. Consume the Core services in the [anti-duplication decision table](docs/architecture.md#core-layer-and-anti-duplication). Add genuinely shared capabilities to Core and extend that table. When features need the same operation, share that operation in Core and keep each feature's gameplay decisions in its own module. For example, Core finds nearby world objects and TameTravel decides which animals may travel. Product, assembly, namespaces and loader identity remain HeimKit. The legacy source tree has been retired.
3. Follow the architecture’s required player-service hookup for every feature and document it in the feature spec. Only explicitly specified offline/server responsibilities in the architecture’s four exception categories may run independently of presence. Give each module its own enable setting, startup state log, compatibility checks and isolated failure handling. Modules must work with other modules disabled; shared classes must not depend on another module being enabled.
4. Use the loader-provided configuration directory. Create `heimkit.cfg` automatically with all defaults when missing; preserve existing values and add missing settings. Keep the optional reference config synchronized with code defaults. Put all shared/non-feature sections before feature sections in generated and reference configuration; no relative feature order is required. Follow the architecture configuration-layout contract when adding shared sections. The documented hidden DisableDebugLogging override is manual-only: preserve supplied values without generating absent keys; all features use the shared suppression resolver.
5. For build and release work, follow the [AI versioning policy](docs/ai/versioning.md) and its linked preparation procedure. Builds still require Trevor's explicit request.
6. Update the relevant spec and user guide when behavior changes. For logging changes, follow the architecture standard-event/grouping contract: document which observed results belong in normal output, which evidence stays in Debug, and the logical boundary used to combine repeated results. Preserve immediate failures/lifecycle transitions and distinct player identities. README feature entries explain user benefits, high-level behavior and essential scope, with guide/specification links. Include a concise compatibility overview; detailed configuration, implementation and operational instructions belong under docs. Follow the README content rules in docs/contributing.md. Keep testing instructions, results and evidence requests in chat only.

Do not install into or restart a live server, change worlds, remove the game-version guard, or change client installations as an incidental part of a code edit. Follow explicit user authorization for operational work.

Do not commit credentials, world saves, proprietary game assemblies, copied BepInEx runtime files, machine-specific reference paths, or generated build output. Inspect staged files before committing. Commit and push when requested; otherwise leave local edits reviewable.

For every Thunderstore package, update the root CHANGELOG.md with concise user-facing release notes, newest version first. The current heading must match the package version and include meaningful change bullets. Publish-Thunderstore.ps1 must require and include this file at the ZIP root. This release changelog is separate from development journals; keep testing instructions, results and evidence out of it.
